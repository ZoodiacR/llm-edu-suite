# Glosario de términos (ES ↔ EN)

[← Volver al índice](README.md)

Los términos se mantienen en inglés cuando es así como aparecen en papers, librerías y ofertas de trabajo. Entre paréntesis, el módulo, la librería o el notebook (NB) donde aparece cada uno.

## Tokenización y arquitectura

| Término | Significado |
|---|---|
| **Token** | Unidad mínima que procesa el modelo: un fragmento de palabra, una palabra frecuente o un byte. |
| **BPE (Byte-Pair Encoding)** | Algoritmo que construye el vocabulario fusionando repetidamente el par de símbolos más frecuente. La variante *byte-level* parte de los 256 bytes, por lo que nunca produce `<UNK>`. (`tokenizer.py`, NB 02) |
| **Fertility** | Número medio de tokens por palabra. Más alto = el tokenizador "rompe" más el texto (típico en idiomas poco representados). |
| **Compression ratio** | Bytes de texto por token. Más alto = secuencias más cortas = inferencia más barata. |
| **Embedding** | Vector aprendido que representa un token (o un documento, o un ítem en recomendación). |
| **Decoder-only / causal LM** | Transformer que predice el siguiente token y solo puede mirar hacia atrás (máscara causal). Es la arquitectura de GPT, Llama, Qwen, DeepSeek y SmolLM2. (`model.py`) |
| **Self-attention** | Cada posición calcula una media ponderada de las demás: `softmax(QKᵀ/√d)·V`. Coste O(T²) en la longitud T. |
| **MHA / GQA / MQA** | *Multi-Head*, *Grouped-Query* y *Multi-Query Attention*. GQA comparte cada cabeza K/V entre varias cabezas Q para reducir la KV-cache. (`layers.py`, NB 03) |
| **MLA (Multi-head Latent Attention)** | Técnica de DeepSeek-V2/V3: comprime K y V en un vector latente pequeño que es lo único que se guarda en caché. |
| **RoPE (Rotary Position Embedding)** | Codifica la posición rotando pares de dimensiones de Q y K; el producto QKᵀ pasa a depender solo de la distancia relativa. Hay dos convenciones para elegir los pares: intercalada (2i, 2i+1), la del Llama original y la nuestra, y *rotate_half* (i, i+d/2), la de Hugging Face; son equivalentes permutando las filas de W_q y W_k. |
| **Checkpoint / safetensors** | Un modelo publicado es código (arquitectura) + `config.json` (hiperparámetros) + pesos. `safetensors` es el formato estándar de pesos: un diccionario nombre → tensor que se carga sin ejecutar código y admite *memory-mapping*. |
| **RMSNorm** | Normalización que solo divide por la raíz cuadrática media (sin restar la media). Más barata que LayerNorm; estándar en Llama. |
| **Pre-norm / sandwich norm / QK-norm** | Dónde se colocan las normalizaciones: antes de cada sub-bloque, antes y después, o sobre Q y K para estabilizar el entrenamiento. |
| **SwiGLU** | FFN con compuerta: `W_down(SiLU(W_gate·x) ⊙ W_up·x)`. Estándar en LLMs modernos. |
| **MoE (Mixture of Experts)** | Sustituye la FFN por N expertos y un *router* que activa solo k de ellos por token: muchos parámetros totales, pocos activos. (NB 05) |
| **Aux-loss vs aux-free balancing** | Dos formas de evitar que el router use siempre los mismos expertos: una pérdida auxiliar, o un sesgo por experto ajustado sin gradiente (DeepSeek-V3). |
| **Shared expert** | Experto que procesa siempre todos los tokens, además de los enrutados. |
| **Sliding-window / Longformer / block-sparse / linear attention** | Variantes de atención eficiente para contextos largos: ventana local, ventana + tokens globales, bloques seleccionados por contenido, y atención lineal de coste O(T). (NB 04) |
| **Attention sink** | Posición (a menudo el primer token o el de fin de secuencia) donde una capa deja aparcada la probabilidad de atención cuando no tiene nada concreto que leer. Hay que conservarla al recortar la KV-cache, y en los mapas de atención tapa el alineamiento real. (NB 04, NB 06; en el NB 00, el 61 % de toda la atención de SmolLM2-135M va al primer token) |
| **Logit lens** | Leer lo que el modelo "diría" en una capa intermedia pasando el estado oculto de esa capa por la normalización final y la cabeza de salida, como si fuera la última capa (nostalgebraist, 2020). Enseña en qué punto de la profundidad se forma una respuesta; es una lectura aproximada, porque la cabeza solo se entrenó con la última capa (el *tuned lens* entrena en su lugar un adaptador pequeño por capa). En el NB 00, con SmolLM2-135M, la respuesta correcta sube del puesto ~550–21.000 en la capa 20 a ser la primera solo en las capas 28–30 de 30. |
| **Encoder-only** | Transformer con atención bidireccional (sin máscara causal): cada token ve a todos los demás. No genera; da a cada posición una representación que depende de toda la entrada. BERT, RoBERTa, DeBERTa, ModernBERT. Se usa para clasificación, entidades, embeddings y rerankers. En el curso, `ModelConfig(causal=False)`. (NB 06) |
| **Encoder-decoder** | Transformer con las dos mitades del original: un encoder bidireccional lee la entrada una vez y un decoder causal escribe la salida leyendo los estados del encoder con *cross-attention*. T5, BART, Flan-T5, Whisper. Fuerte en traducción y voz. (NB 06) |
| **MLM (masked language modeling)** | Objetivo de preentrenamiento de BERT: se oculta el 15 % de las posiciones (80 % `[MASK]`, 10 % token aleatorio, 10 % sin cambiar) y el modelo las recupera usando los dos lados. Solo puntúa las posiciones ocultas; ELECTRA aprovecha todas con *replaced token detection*. (NB 06) |
| **Cross-attention** | Atención cuyas consultas vienen de una secuencia (la salida que escribe el decoder) y cuyas claves y valores vienen de otra (los estados del encoder). En T5, cada bloque del decoder es self-attention → cross-attention → FFN. (NB 06) |
| **[CLS] / pooling** | Dos formas de resumir una frase en un vector a partir de un encoder: el estado del token especial inicial `[CLS]`, o la media de los estados de todos los tokens (*mean pooling*, ignorando el padding con la máscara de atención). (NB 06) |
| **Classification head** (cabeza de clasificación) | Capa lineal sobre el vector de la frase que da una distribución sobre un conjunto fijo de etiquetas, `softmax(W·h + b)`. `AutoModelForSequenceClassification` la añade inicializada al azar y se ajusta junto con el encoder. (NB 06) |
| **ModernBERT** | Encoder de 2024 (Warner et al.) que aplica a BERT lo aprendido por los decoders: RoPE, GeGLU, pre-norm, capas globales alternadas con ventanas de 128 tokens, *unpadding* y 8.192 tokens de contexto. La versión base (150M) llega al 93,0 % en Banking77 ajustada. (NB 06) |
| **Linear probe** | Clasificador lineal (por ejemplo, regresión logística) entrenado sobre representaciones congeladas. Mide cuánta información útil para la tarea contienen ya; en el NB 06, ModernBERT congelado da 89,2 % y `nomic-embed-text` 93,3 % en Banking77. En el NB 22, una regresión logística sobre los embeddings de imagen de CLIP, congelados, pasa del 34,3 % con una imagen por raza al 89,0 % con todas (~100). |

## Datos de pre-entrenamiento

| Término | Significado |
|---|---|
| **FineWeb / FineWeb-Edu** | Corpus abiertos de Hugging Face (Penedo et al., 2024) construidos a partir de Common Crawl con cada paso del pipeline (filtros, deduplicación) validado por ablaciones con modelos pequeños. FineWeb-Edu es el subconjunto con nota educativa de 3 o más según un clasificador. Licencia ODC-By. En el NB 07 se usan muestras de 12.000 y 1.000 documentos, descargadas en `data/cache/` y no redistribuidas. |
| **Deduplication** (deduplicación) | Quitar documentos repetidos del corpus. La **exacta** compara un hash (por ejemplo SHA-1) del texto normalizado: lineal y barata, pero un solo carácter cambiado la derrota. La de **casi-duplicados** usa MinHash + LSH. Reduce cómputo, memorización y fugas de evaluación. (NB 07) |
| **Near-duplicate** (casi-duplicado) | Documento que es casi el mismo que otro: la misma página con otra plantilla, o con unas pocas palabras cambiadas. El hash exacto no lo ve; se detecta por el solapamiento de shingles (similitud de Jaccard). (NB 07) |
| **Shingle** | Cada uno de los n-gramas solapados (de palabras o de caracteres) en que se descompone un documento para compararlo con otros como conjunto. Con 5-gramas de palabras, editar una palabra rompe hasta cinco shingles. (NB 07) |
| **Jaccard similarity** (similitud de Jaccard) | Solapamiento entre dos conjuntos, `J(A, B) = \|A ∩ B\| / \|A ∪ B\|`, entre 0 y 1. Sobre conjuntos de shingles mide cuánto texto comparten dos documentos. (NB 07) |
| **MinHash** | Estimador de la similitud de Jaccard (Broder, 1997): se aplica una función hash aleatoria a cada shingle y se guarda el mínimo; la probabilidad de que dos documentos tengan el mismo mínimo es exactamente su Jaccard. Con k funciones hash, la firma de k mínimos estima J con error típico `√(J(1−J)/k)`. En el NB 07, k = 128 funciones afines módulo un primo de Mersenne. |
| **LSH (locality-sensitive hashing)** | Forma de encontrar pares candidatos sin comparar todos con todos: la firma MinHash se parte en b bandas de r filas y dos documentos son candidatos si coinciden en alguna banda entera. La probabilidad, `1 − (1 − J^r)^b`, es una curva en S con umbral cerca de `(1/b)^(1/r)`; con 16 × 8, unos 0,71. (NB 07) |
| **Quality filter** (filtro de calidad) | Paso que descarta documentos poco útiles para entrenar. Los **heurísticos** (reglas de Gopher y C4: longitud, símbolos, viñetas, stop words, líneas sin puntuación final) quitan lo que no es prosa; los **basados en modelo** (el clasificador de FineWeb-Edu, un BERT de 110M; el fastText de DCLM) puntúan cuánto vale el texto, con el sesgo de quien etiquetó sus datos. (NB 07) |
| **Decontamination** (descontaminación) | Quitar (o declarar) los documentos de entrenamiento que contienen texto de los benchmarks de evaluación, normalmente buscando n-gramas largos compartidos (8 a 13 tokens). Atrapa las copias literales, no las paráfrasis. En el NB 07 encuentra las 50 fugas plantadas y 29 solapes naturales de noticias sindicadas. |
| **Model collapse** | Pérdida progresiva de diversidad cuando un modelo se entrena repetidamente con texto generado por modelos: las colas de la distribución desaparecen primero (Shumailov et al., 2024). Por eso los datos sintéticos se deduplican, se filtran y se mide su diversidad (por ejemplo, bigramas distintos: 0,60 en el texto de `qwen2.5:3b` frente a 0,72 en texto humano, NB 07). |

## Entrenamiento y post-training

| Término | Significado |
|---|---|
| **Pre-training** | Entrenar desde cero prediciendo el siguiente token sobre un corpus grande. Lo que pasa antes con los datos está en [Datos de pre-entrenamiento](#datos-de-pre-entrenamiento). (NB 08) |
| **Perplexity** | `exp(pérdida media)`. Intuición: entre cuántos tokens "duda" el modelo. Menor es mejor. |
| **Warmup / cosine / WSD** | Planes de *learning rate*: subida inicial; bajada en coseno; o *Warmup-Stable-Decay* (constante y caída final). |
| **AdamW / weight decay** | Optimizador estándar. El *weight decay* no se aplica a normas ni a biases (grupos de parámetros). |
| **Gradient accumulation / clipping / AMP** | Simular lotes grandes, limitar la norma del gradiente y usar precisión mixta (bf16/fp16). |
| **Gradient checkpointing / activation checkpointing** | Recalcular las activaciones durante el *backward* en lugar de guardarlas (en PyTorch, `torch.utils.checkpoint.checkpoint` alrededor de cada bloque): menos memoria a cambio de un ~30 % más de cómputo. Activado por defecto en `scripts/finetune.py`. En el NB 09 recorta el pico de memoria un 57 % en fp32 por un ~22 % más de tiempo por paso. |
| **Mixed precision / bf16** (precisión mixta) | Calcular en bf16 o fp16 en los tensor cores y guardar los pesos maestros en fp32. bf16 tiene el rango de exponente de fp32 y no necesita *loss scaling*; fp16 sí. En PyTorch, `torch.autocast("cuda", dtype=torch.bfloat16)`. (NB 09: paso 2,2× más rápido que en fp32) |
| **MFU (model FLOPs utilization)** | Fracción del pico de FLOP/s de la GPU que es trabajo útil del modelo: tokens/s × 6N FLOPs por token (más la atención) dividido por el pico. Los entrenamientos grandes bien ajustados llegan al 40–60 %. (NB 09: 32 %) |
| **DDP (DistributedDataParallel)** | Paralelismo de datos de PyTorch: un proceso por GPU, cada uno con el modelo entero y su trozo del batch; un all-reduce promedia los gradientes antes del paso del optimizador, así que equivale a entrenar con el batch global. (NB 09) |
| **All-reduce** | Operación colectiva que suma (o promedia) un tensor entre todos los procesos y deja el resultado en todos. En anillo, cada proceso envía unos 2(k−1)/k · P bytes para un tensor de P bytes, casi independiente del número de procesos k. NCCL en GPU, gloo en CPU. |
| **ZeRO (Zero Redundancy Optimizer)** | Técnica de DeepSpeed (Rajbhandari et al., 2020) que reparte entre las GPUs de datos, en lugar de replicarlos, los estados del optimizador (etapa 1), también los gradientes (etapa 2) y también los pesos (etapa 3). Con 8 GPUs, un 7B pasa de 112 GB por GPU a 14 GB en la etapa 3. (NB 09) |
| **FSDP (Fully Sharded Data Parallel)** | La versión de ZeRO-3 de PyTorch (`fully_shard` en FSDP2): cada GPU guarda un trozo de los pesos, los gradientes y los estados, y hace all-gather de los pesos de cada capa justo antes de usarlos. |
| **Tensor parallelism** (paralelismo de tensor) | Partir cada matmul entre GPUs (por columnas y por filas, como Megatron-LM), con un all-reduce dentro de cada capa. Necesita enlaces rápidos, así que se usa dentro de un nodo (NVLink). |
| **Pipeline parallelism** (paralelismo de pipeline) | Repartir las capas en etapas, una por grupo de GPUs, y pasar micro-batches de una a otra. Paga una "burbuja" de tiempo ocioso al llenar y vaciar el pipeline (GPipe, 1F1B). |
| **SFT (Supervised Fine-Tuning)** | Ajustar el modelo con pares instrucción→respuesta, normalmente renderizados con la **plantilla de chat** del modelo. (NB 13) |
| **Completion-only loss / loss masking** | Calcular la pérdida de SFT solo sobre los tokens de la respuesta: los del prompt reciben la etiqueta `-100` y la entropía cruzada los ignora. TRL lo hace automáticamente con datasets *prompt-completion*. (NB 13) |
| **SFTTrainer** | El *trainer* de TRL para SFT: acepta un dataset conversacional o prompt-completion, aplica la plantilla de chat, enmascara el prompt y admite un `peft_config` para entrenar adaptadores LoRA. Se configura con `SFTConfig`. (`scripts/finetune.py`, NB 13) |
| **LoRA** | Congela W y aprende una corrección de rango bajo `W + (α/r)·B·A`. Con B=0 al inicio, el modelo arranca idéntico al base; tras entrenar se puede *fusionar* (`merge_and_unload` en `peft`) sin coste en inferencia. (NB 13) |
| **LoRA `modules_to_save`** | Opción de `peft` que entrena (y guarda) copias completas de los módulos elegidos junto a los adaptadores, típicamente el embedding y el `lm_head`. Hace falta cuando el fine-tuning introduce tokens que el modelo base nunca aprendió, como nuevos tokens de rol del chat. (NB 13) |
| **QLoRA** | LoRA sobre un modelo base cuyos pesos congelados se guardan a 4 bits (NF4); los adaptadores siguen en bf16 y cada multiplicación descuantiza el peso primero. Ahorra memoria de pesos (un 7B pasa de ~14 GB a ~3,6 GB), no de activaciones, y cada paso es algo más lento. En `transformers`, `BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4", ...)` + `prepare_model_for_kbit_training`. (NB 13) |
| **Double quantization** (doble cuantización) | Cuantizar también las escalas de cada bloque (a 8 bits): el sobrecoste baja de 0,5 a unos 0,127 bits por parámetro. Una de las tres ideas de QLoRA (`bnb_4bit_use_double_quant=True`). (NB 13) |
| **Paged optimizer** (optimizador paginado) | El estado del optimizador vive en memoria unificada de CUDA y se pagina a la RAM cuando un pico de memoria lo exige, en lugar de fallar con un out-of-memory (`optim="paged_adamw_8bit"`). (NB 13) |
| **Distillation** | Un modelo *student* aprende a imitar la distribución de un *teacher* (KL entre logits). (NB 13) |
| **Model merging** (fusión de modelos) | Combinar varios fine-tunings del mismo base en un solo juego de pesos con aritmética, sin datos ni entrenamiento. Con adaptadores, `add_weighted_adapter` de `peft`; con modelos completos, `mergekit`. Pone los comportamientos uno al lado del otro, pero no los combina en una habilidad nueva; si tienes todos los datos, entrenar multitarea suele salir mejor. (NB 13) |
| **Task vector** | Lo que cambió un fine-tuning: `τ = θ_ajustado − θ_base` (Ilharco et al., 2023). Con LoRA, `(α/r)·B·A` en cada matriz adaptada. Dos task vectors de tareas sin relación son casi ortogonales (en el NB 13, coseno medio +0,012). (NB 13) |
| **Task arithmetic** | Fusionar sumando (o restando) task vectors: `θ = θ_base + Σ λ_t·τ_t`. Sumar da un modelo que hace las dos tareas; restar quita un comportamiento. Para LoRA, `combination_type="cat"` o `"svd"` en `peft` lo calcula de forma exacta. (NB 13) |
| **Model soup** | La media de varios fine-tunings de la misma tarea con hiperparámetros distintos (Wortsman et al., 2022): a menudo mejor y más robusta que la mejor ejecución individual, sin coste extra en inferencia. (NB 13) |
| **Linear mode connectivity** | Dos fine-tunings del mismo modelo preentrenado están unidos por un camino recto en el espacio de pesos a lo largo del cual la pérdida sigue baja (Frankle et al., 2020). Por eso funciona promediar o sumar sus pesos, y por eso no funciona con redes entrenadas desde inicializaciones aleatorias distintas. (NB 13) |
| **TIES-Merging** | Método de fusión para task vectors que se solapan (Yadav et al., 2023): *recorta* cada uno a sus valores más grandes, *elige* un signo por coordenada y promedia solo los valores que coinciden con él. Útil cuando muchos fine-tunings interfieren; con adaptadores casi ortogonales (NB 13) solo tiró señal. |
| **DARE (Drop And REscale)** | Descarta al azar una fracción `p` de las coordenadas de un task vector y reescala el resto por `1/(1−p)` (Yu et al., 2024). Las actualizaciones del fine-tuning son tan redundantes que se puede quitar el 90 % o más. Se suele combinar con la elección de signo de TIES (`dare_ties`). (NB 13) |
| **SLERP** | Interpolación lineal esférica: mezcla dos modelos sobre la esfera en lugar de en línea recta, lo que conserva la norma de los pesos. Un método muy usado en `mergekit`; solo para dos modelos a la vez. (NB 13) |
| **mergekit** | La herramienta de referencia para fusionar modelos completos (Goddard et al., 2024): lineal, SLERP, task arithmetic, TIES, DARE y más, configurada en YAML, en CPU o GPU. Está detrás de muchos de los modelos abiertos fusionados de los leaderboards públicos. (NB 13) |
| **RLHF / preference tuning** | Alinear el modelo con preferencias humanas: respuesta elegida vs rechazada. (NB 14) |
| **DPO (Direct Preference Optimization)** | Optimiza las preferencias directamente, sin modelo de recompensa: `−log σ(β·[(log π−log π_ref)(y_w) − (log π−log π_ref)(y_l)])`. Al inicio vale ln 2. |
| **DPOTrainer** | El *trainer* de TRL para DPO y sus variantes (`loss_type`). Con un `peft_config`, el modelo de referencia es la misma red con el adaptador desactivado, así que no se guarda una segunda copia en memoria. Se configura con `DPOConfig` (`beta`, `loss_type`, `loss_weights`). (`scripts/finetune.py`, NB 14) |
| **Likelihood displacement / DPO + NLL (RPO)** | Efecto por el que DPO agranda el margen bajando la probabilidad de *ambas* respuestas, elegida y rechazada. Se contrarresta sumando la NLL (pérdida SFT) de la respuesta elegida: en TRL, `loss_type=["sigmoid", "sft"]`. |
| **GRPO (Group Relative Policy Optimization)** | RL de DeepSeekMath/R1: muestrea un grupo de respuestas por prompt y usa como ventaja la recompensa normalizada dentro del grupo (sin *critic*). Un grupo en el que todas las muestras tienen la misma recompensa no aporta gradiente. (NB 14 con TRL; el NB 31 lo escribe a mano en unas 30 líneas: 8 muestras por prompt, 32 prompts por paso, β = 0,04 y una actualización por lote) |
| **GRPOTrainer** | El *trainer* de TRL para GRPO: acepta un dataset de prompts y una o varias **funciones de recompensa** en Python `(completions, **columnas) -> list[float]`, muestrea `num_generations` respuestas por prompt y optimiza la política con penalización KL (`beta`). Se configura con `GRPOConfig`. (`scripts/finetune.py`, NB 14) |
| **Verifiable reward** | Recompensa calculable por programa (¿es correcta la respuesta?), sin juez humano ni modelo. Una recompensa *densa* da crédito parcial, así que es menos probable que los grupos empaten. |
| **KL penalty** | Término que impide que la política se aleje demasiado del modelo de referencia. |
| **k3 KL estimator** (estimador k3 de la KL) | La estimación por token de la KL respecto a la referencia que usa DeepSeekMath en GRPO: `π_ref/π_θ − log(π_ref/π_θ) − 1`, calculada con las dos log-probabilidades del token muestreado. Es insesgada y siempre positiva, a diferencia del simple cociente logarítmico. En el NB 31 se queda en unos 0,05 por token durante R1-Zero. |
| **Groups with no signal / zero-advantage groups** (grupos sin señal) | En GRPO, un grupo en el que todas las muestras reciben la misma recompensa (todas bien o todas mal): todas las ventajas son cero, así que no aporta nada al gradiente. Su proporción es el diagnóstico clave de un entrenamiento con RL: a medida que el modelo mejora, los problemas se resuelven siempre y dejan de enseñar. El muestreo dinámico de DAPO los filtra. En el NB 31 la proporción sube del 53 % al 80 % durante R1-Zero, y es del 88 % desde el primer paso después del arranque en frío. |
| **Cold start (SFT)** (arranque en frío) | En la receta de R1, un SFT pequeño con cadenas de pensamiento seleccionadas antes del RL, para arreglar el formato y la legibilidad que le faltaban a R1-Zero. En el NB 31, 200 pasos sobre 300 soluciones desarrolladas llevan el modelo base del 69,4 % al 100,0 %, cuando R1-Zero necesitó unos 217 pasos de RL de 256 muestras para superar el 90 % de recompensa. |

## Razonamiento y cómputo en inferencia

| Término | Significado |
|---|---|
| **Chain of thought (CoT)** (cadena de pensamiento) | Hacer que el modelo escriba sus pasos intermedios antes de la respuesta, con ejemplos resueltos en el prompt (few-shot, Wei et al., 2022) o con un simple "piensa paso a paso" (zero-shot). Un transformer hace una cantidad fija de trabajo por token, así que los pasos escritos son lo que le da cómputo en serie. En el NB 15 lleva a `qwen2.5:3b` del 12,5 % al 85,0 % en GSM8K. |
| **Test-time compute** (cómputo en inferencia) | Cómputo que se gasta en inferencia en un solo problema: razonar más largo, varias muestras, un verificador, revisiones. Snell et al. (2024) lo tratan como un eje de escalado propio, junto a los parámetros y los datos. Se paga en tokens de salida, los lentos y caros. (NB 15) |
| **Self-consistency** | Muestrear varias cadenas de pensamiento a temperatura > 0 y devolver la respuesta final más frecuente (Wang et al., 2022): los caminos correctos tienden a coincidir y los erróneos se dispersan. Necesita respuestas que se puedan comparar exactamente. (NB 15: 85,0 % con 5 muestras, lo mismo que greedy; pass@5 92,5 %) |
| **maj@k** | Acierto del voto por mayoría entre k muestras, es decir, de la self-consistency con k muestras. Sube con k y se satura. (NB 15) |
| **pass@k** | Probabilidad de que al menos una de k muestras sea correcta: el techo que alcanzaría un verificador perfecto con esas muestras. La distancia entre pass@k y maj@k es lo máximo que un verificador puede añadir sobre el voto. Estimador sin sesgo con n muestras y c correctas: `1 − C(n−c, k) / C(n, k)` (Chen et al., 2021). (NB 15: 80,0 % con k = 1, 92,5 % con k = 5) |
| **Best-of-N** | Generar N candidatas y devolver la que mejor puntúa un verificador o un modelo de recompensa. Solo ayuda si el verificador discrimina mejor que un voto; con uno débil, elige respuestas incorrectas pero bien escritas. (NB 15: 80,0 % con un juez de 7B frente al 85,0 % del voto) |
| **Verifier / reward model (ORM, PRM)** (verificador / modelo de recompensa) | Un modelo o un programa que puntúa una respuesta candidata. Un modelo de recompensa de *resultado* (ORM) puntúa la respuesta final (Cobbe et al., 2021); uno de *proceso* (PRM), cada paso (Lightman et al., 2023). Los verificadores programáticos (tests, una calculadora, un solver, un esquema) son los más fiables. (NB 14, NB 15) |
| **Reasoning model** (modelo de razonamiento) | Un modelo entrenado para pensar en largo antes de responder, normalmente con RL y recompensas verificables (o1, DeepSeek-R1) o por destilación de las trazas de razonamiento de otro modelo (R1-Distill). El pensamiento se emite como tokens, a menudo dentro de `<think>...</think>`, y se cobra como salida. (NB 15: R1-Distill 1.5B, 63,7 % con 870 tokens por problema) |
| **R1-Zero** | El modelo de DeepSeek entrenado con RL y solo un verificador, directamente desde el modelo base, sin ejemplos supervisados de razonamiento (DeepSeek-AI, 2025). Aprendió a pensar más largo por su cuenta, pero sus respuestas costaba leerlas, y por eso R1 añade un arranque en frío. En el NB 31, GRPO desde el modelo base del curso, de 1,6M de parámetros, sube la exactitud del 69,4 % al 99,8 % y la proporción de muestras que razonan del 11 % al 67 %; el base, obligado a razonar, ya sacaba un 99,9 %, así que el RL sacó a la luz una habilidad que había puesto el preentrenamiento. |
| **Length generalization** (generalización en longitud) | Si un modelo entrenado con problemas de hasta cierta longitud (o número de pasos) sigue resolviendo los más largos. Los transformers entrenados con aritmética no suelen conseguirlo sin ayuda de la codificación de posiciones o del formato de los datos (index hints, embeddings Abacus). En el NB 31, los modelos entrenados con cadenas de 1 a 6 operaciones se quedan entre el 14,8 % y el 22,6 % con cadenas de 8 a 10, cerca del azar (10 %), y las index hints empeoraron los resultados con ese tamaño. |
| **Overthinking** | Razonar más de lo que pide el problema: bucles, dudas que vuelven atrás, o agotar el presupuesto de tokens antes de responder. En el NB 15, 16 de las 80 respuestas de R1-Distill 1.5B llegan al límite de 2.048 tokens. |
| **Reasoning effort (`effort`)** (esfuerzo de razonamiento) | Un parámetro de la API que fija cuánto piensa un modelo de razonamiento antes de responder: el `effort` de Anthropic (`low` … `max`), el `reasoning_effort` de OpenAI, el presupuesto de pensamiento de Gemini. Con *adaptive thinking* el modelo decide además si piensa o no, y los tokens de pensamiento se cobran como salida. En el NB 15, Claude Haiku 5.5 escribió un bloque de pensamiento en el 4 % de las respuestas con `low` y en el 100 % con `max`, con un acierto dentro del ruido hasta `max` (del 92,5 % al 98,8 %) por entre 174 y 674 tokens de salida: en una tarea fácil, sobre todo un mando de coste y latencia. |
| **Bradley-Terry** | Modelo de comparaciones por pares: i gana a j con probabilidad `σ(β_i − β_j)`, con las β ajustadas por máxima verosimilitud (Bradley y Terry, 1952). Está detrás de los modelos de recompensa de RLHF, de DPO y del ranking de Chatbot Arena; Elo es una aproximación online. (NB 14, NB 15) |
| **Position bias** (sesgo de posición) | Que un juez por pares (humano o LLM) prefiera la primera o la segunda respuesta sin mirar el contenido (Zheng et al., 2023). Se mide y se controla juzgando cada par en los dos órdenes y quedándose solo con los veredictos coherentes. En el NB 15, el juez de 7B mantuvo el veredicto solo en el 47 % de 30 pares al cambiar el orden. |

## Inferencia y sistemas

| Término | Significado |
|---|---|
| **KV-cache** | Guardar K y V de los tokens ya procesados para no recalcularlos en cada paso de generación. Su tamaño suele ser el cuello de botella de memoria. (NB 03, 10) |
| **Prefill / decode** | Fase de procesar el prompt (paralela) y fase de generar token a token (secuencial, limitada por memoria). |
| **TTFT (time to first token)** (tiempo hasta el primer token) | Desde que se envía una petición hasta que llega el primer token: tiempo en cola + prefill + red. Crece con la longitud del prompt y con la cola. (NB 10, 12: de 101 a 645 ms entre 338 y 2.322 tokens de prompt) |
| **TPOT / inter-token latency** (tiempo por token de salida / latencia entre tokens) | *Time per output token*: el hueco entre tokens durante el decode. 1 / TPOT es la velocidad de lectura de un usuario; la latencia de extremo a extremo ≈ TTFT + TPOT × (tokens de salida − 1). El batching lo sube. (NB 12: 12,5 ms con una secuencia, 23 ms con cuatro por paso) |
| **Throughput / goodput** | Throughput: tokens de salida por segundo sumando todos los usuarios, de lo que depende la factura del hardware. Goodput: las peticiones por segundo que cumplen el SLO de latencia, la capacidad que de verdad cuenta (DistServe). |
| **Greedy / temperature / top-k / top-p** | Estrategias de muestreo: el más probable; aplanar o afilar la distribución; quedarse con los k más probables; o con el núcleo de probabilidad acumulada p. `model.next_token_distribution` muestra la distribución resultante. |
| **Speculative decoding** | Un modelo pequeño (*draft*) propone varios tokens y el grande los verifica en un solo paso. Con el esquema de aceptación correcto, la distribución de salida es **idéntica** a la del modelo grande. (`inference.py`, NB 10) |
| **Continuous batching** (batching continuo) | Batching planificado en cada paso de decode: las secuencias entran y salen del batch según llegan y terminan, en lugar de esperar a la más larga (batching estático). Lo introdujo Orca (Yu et al., 2022); es lo estándar en vLLM, SGLang y TGI. |
| **PagedAttention** | La forma de vLLM de guardar la KV-cache en bloques de tamaño fijo con una tabla de bloques, como las páginas de la memoria virtual: casi sin fragmentación, con bloques compartidos entre secuencias y muchas más secuencias simultáneas por GPU (Kwon et al., 2023). |
| **Slot** | En llama.cpp y Ollama, una de las secuencias del batch que el servidor ejecuta en paralelo, con su parte de la KV-cache. Su número es fijo (`OLLAMA_NUM_PARALLEL`); las peticiones que no caben esperan en una cola. (NB 12: un slot frente a cuatro) |
| **Prefix caching / prompt caching** (caché de prefijos / de prompts) | Guardar la KV-cache de un prefijo que comparten muchas peticiones (system prompt, herramientas, documentos) y reutilizarla en lugar de repetir el prefill: automatic prefix caching en vLLM, RadixAttention en SGLang, la caché de un slot en llama.cpp; los proveedores lo venden como *prompt caching*, con los tokens de entrada cacheados más baratos. La coincidencia es token a token desde el principio, así que lo compartido va primero. (NB 12: el 99,1 % del prompt sale de la caché, TTFT de 654 a 39 ms) |
| **Little's law** (ley de Little) | L = λW: peticiones en el sistema = tasa de llegada × tiempo en el sistema, en cualquier cola estable (Little, 1961). Convierte la planificación de capacidad en una cuenta. (NB 12: 1,33 peticiones/s × 3,00 s = 4,0 en vuelo) |
| **Quantization (INT8 / INT4 / NF4)** | Guardar pesos con menos bits. *absmax* escala por el máximo absoluto; por bloques reduce el error; NF4 usa niveles óptimos para pesos con distribución normal. (NB 11) |
| **optimum-quanto** | Librería de Hugging Face que cuantiza en el sitio un modelo de PyTorch / `transformers`: `quantize(model, weights=qint8 / qint4 / qfloat8)` sustituye las capas lineales por versiones cuantizadas y `freeze(model)` guarda los pesos cuantizados. Funciona en CPU y GPU. (NB 11) |
| **NF4 (NormalFloat4)** | Formato de 4 bits con 16 niveles colocados en los cuantiles de una normal, con una escala absmax por bloque de 64 pesos. Como los pesos preentrenados son aproximadamente normales, pierde menos precisión que int4 con niveles equiespaciados. Es el formato de QLoRA (`bitsandbytes`). (NB 13, 11) |
| **GGUF / Q4_K_M** | El formato de fichero y el esquema de cuantización a 4 bits por bloques que usan llama.cpp y Ollama. `qwen2.5:3b` en Ollama es un GGUF Q4_K_M de unos 1,9 GB. |
| **k-quants** | La familia de tipos de cuantización GGUF de llama.cpp (de Q2_K a Q6_K): superbloques de 256 pesos divididos en subbloques con escalas cuantizadas, dejando algunos tensores sensibles en más precisión (el sufijo `_S` / `_M` / `_L`). Q8_0 son bloques sencillos de 32 valores en 8 bits. (NB 12: `qwen2.5:1.5b-instruct` en Q4_K_M ocupa 1,17 GB de GPU y decodifica a 130 tok/s, frente a 3,28 GB y 64 tok/s en FP16) |
| **Gateway (LLM gateway)** | Un servicio entre las aplicaciones y los modelos que les da una única API (normalmente compatible con OpenAI) y resuelve en un solo sitio el enrutado, los reintentos, los fallbacks, los timeouts, los límites de tasa, los presupuestos, la caché y los logs. LiteLLM, Portkey, OpenRouter, los AI gateways de la nube. (NB 12) |
| **Fallback / circuit breaker** | Un fallback manda la petición al siguiente modelo de una cadena cuando uno falla o agota su timeout. Un circuit breaker deja de mandar tráfico durante un rato a un backend que falla, para no machacarlo mientras se recupera. Los dos necesitan logs, o esconden un modelo principal caído. (NB 12) |
| **Cascade / model router** (cascada / router de modelos) | Dos formas de enrutar por coste. Una cascada (FrugalGPT) pregunta primero al modelo barato y solo escala al caro cuando salta una señal de incertidumbre; un router (RouteLLM) predice antes de llamar a nadie qué modelo necesita cada petición. No hay que confundirlo con un nodo router de LangGraph, que elige un especialista, no un tamaño de modelo. (NB 12: una cascada 3B → 7B, 85,0 % con el 88 % del tiempo de GPU de usar siempre el 7B; NB 20: un voto de vecinos más cercanos que solo manda al LLM el 3 % de mensajes ambiguos, 0,922 frente a 0,926 de usar siempre el 7B, con 1/50 de su latencia) |
| **Ollama** | Servidor local de modelos abiertos: `ollama pull` descarga un modelo y el servidor (puerto 11434) ofrece una API propia y otra compatible con OpenAI (`/v1`). Es el proveedor por defecto del curso para los notebooks de aplicaciones que llaman a un LLM (16, 18, 19, 23, 25, 26, 28) (`qwen2.5:3b`, `nomic-embed-text`), usado a través de `ChatOllama` / `OllamaEmbeddings` de `langchain-ollama`. |
| **Arithmetic intensity / roofline** (intensidad aritmética) | FLOPs por byte movido de memoria. El modelo roofline acota el rendimiento por el mínimo entre el pico de FLOP/s y intensidad × ancho de banda: las matmuls grandes están limitadas por cómputo; las operaciones elemento a elemento, el softmax y el decode con batch pequeño, por memoria. (NB 10, 09) |
| **FlashAttention** | Kernel de atención exacto e *IO-aware* (Dao et al., 2022): calcula por bloques en la SRAM del chip con un softmax online y nunca escribe la matriz T × T en HBM, así que su memoria es lineal en T. FlashAttention-2 no viene en las wheels de PyTorch para Windows; allí SDPA usa los kernels memory-efficient o cuDNN, con la misma idea. (NB 09) |
| **Kernel fusion / `torch.compile`** (fusión de kernels) | Juntar varias operaciones en un solo kernel de GPU que lee y escribe la memoria una sola vez. `torch.compile` captura el grafo del modelo y su backend por defecto, `inductor`, genera kernels de Triton (no disponible en Windows). (NB 09) |
| **CUDA graph** | Grabar una secuencia de kernels una vez y reproducirla con un solo lanzamiento, quitando el coste de CPU de lanzar cada kernel; exige formas estáticas. `torch.compile(backend="cudagraphs")`; los servidores de inferencia lo usan en el decode. (NB 09: 4,1× en el forward de un modelo pequeño) |

## Embeddings y rerankers

| Término | Significado |
|---|---|
| **Bi-encoder** | Modelo de recuperación que codifica la consulta y el documento *por separado*, en un vector cada uno (un encoder más un pooling: la media de los vectores de los tokens o el vector `[CLS]`), y los puntúa por similitud coseno. Los vectores de los documentos se calculan una sola vez, offline, así que buscar cuesta una pasada para la consulta más una búsqueda vectorial. Es lo que en recuperación se llama "modelo de embeddings": all-MiniLM, BGE, E5, nomic-embed. (NB 17) |
| **Cross-encoder** | Modelo que lee la consulta y el documento *juntos* en un solo transformer y devuelve una puntuación de relevancia, de modo que cada token de la consulta atiende a cada token del documento. Es más preciso que un bi-encoder, pero necesita una pasada por candidato, así que solo se usa para reordenar una lista corta. (NB 17: ms-marco-MiniLM-L6-v2, bge-reranker-base) |
| **Late interaction (ColBERT)** (interacción tardía) | Punto intermedio entre bi-encoder y cross-encoder: se guarda un vector por token y la puntuación es la suma, sobre los tokens de la consulta, del token del documento que mejor encaja (MaxSim) (Khattab y Zaharia, 2020). ColPali lo aplica a imágenes de páginas. |
| **Retrieve-then-rerank** (recuperar y reordenar) | El embudo de recuperación en dos etapas: una primera etapa barata (BM25, embeddings o ambos) devuelve 50–100 candidatos y un cross-encoder los reordena. Es la misma idea que el embudo de recomendación. Un reranker solo puede subir lo que encontró la primera etapa, así que el recall@100 de esta es su techo. (NB 23, NB 17) |
| **Contrastive learning / InfoNCE** (aprendizaje contrastivo) | Entrenar embeddings para que una consulta quede cerca de sus documentos relevantes y lejos del resto. La pérdida InfoNCE (van den Oord et al., 2018) es una entropía cruzada sobre el batch en la que la "clase" de cada consulta es su propio documento, con las similitudes divididas por una **temperatura** τ (a menudo 0,01–0,05). `sentence-transformers` la llama `MultipleNegativesRankingLoss` y la escribe como `scale = 1/τ = 20`. (NB 17: a mano y con la librería sale el mismo 0,18594) |
| **In-batch negatives** (negativos del batch) | En un batch de B pares (consulta, positivo), los otros B − 1 documentos hacen de negativos para cada consulta, sin coste adicional. Con batches más grandes la tarea es más difícil y los embeddings salen mejores. `BatchSamplers.NO_DUPLICATES` evita que el mismo texto aparezca dos veces en un batch, donde actuaría como falso negativo. (NB 17) |
| **Hard negatives** (negativos difíciles) | Negativos que un recuperador (BM25 o un modelo anterior) pone arriba pero que no son relevantes: los casos que de verdad confunden al modelo, y el ingrediente principal de DPR y de las recetas modernas. Un negativo minado puede ser un positivo sin etiquetar (falso negativo); lo habitual es filtrarlos con la puntuación de un reranker. (NB 17: un negativo difícil de BM25 por par llevó al MiniLM ajustado de 0,723 a 0,762 de nDCG@10) |
| **Task prefix** (prefijo de tarea) | Texto fijo que los modelos de embeddings asimétricos esperan delante de consultas y documentos, como `search_query:` / `search_document:` (nomic) o `query:` / `passage:` (E5). Olvidarlo es un fallo silencioso: nada se rompe, solo baja la calidad. (NB 17: +0,006 para nomic en SciFact, dentro del ruido) |
| **Matryoshka embeddings (MRL)** | Embeddings entrenados con la pérdida contrastiva sumada sobre varias longitudes de prefijo (p. ej. 384, 256, 128, 64), de modo que las primeras m dimensiones son por sí solas un buen embedding y los vectores se pueden truncar a posteriori (Kusupati et al., 2022). Así están entrenados `text-embedding-3` de OpenAI (`dimensions=`) y nomic-embed v1.5. (NB 17: 0,646 con 64 dimensiones frente a 0,589 sin esa pérdida) |
| **Embedding quantization (int8 / binary)** (cuantización de embeddings) | Guardar cada dimensión de un vector en un byte (int8, 4 veces más pequeño, calibrado sobre el corpus) o en un bit de signo (binaria, 32 veces más pequeño, comparada con la distancia de Hamming). No es lo mismo que cuantizar los pesos de un modelo. `sentence_transformers.quantization.quantize_embeddings`. (NB 17: 48 bytes por documento en lugar de 1.536) |
| **Rescoring** | Recuperar candidatos con códigos baratos (binarios) y reordenar los primeros con vectores más precisos (float o int8), lo que recupera casi toda la calidad perdida. Reordena, pero no cambia el recall. (NB 17: binario 0,709 → 0,760 con rescoring int8, frente al 0,762 de float32) |
| **BEIR** | Colección de conjuntos de recuperación heterogéneos para evaluar sin ajuste previo (*zero-shot*) (Thakur et al., 2021), con nDCG@10 como métrica principal. Mostró que BM25 es una línea base difícil de batir fuera de dominio. SciFact y NFCorpus, los del NB 17, son dos de sus conjuntos. |
| **MTEB** | Massive Text Embedding Benchmark (Muennighoff et al., 2023): decenas de tareas (recuperación, clasificación, clustering, similitud…) y el ranking del que se eligen la mayoría de los modelos de embeddings. Es un punto de partida, no una respuesta: promedia muchas tareas y los conjuntos públicos pueden colarse en el entrenamiento. |
| **sentence-transformers** | Librería de Hugging Face para bi-encoders (`SentenceTransformer`), cross-encoders (`CrossEncoder`), sus pérdidas (`MultipleNegativesRankingLoss`, `MatryoshkaLoss`), su entrenamiento (`SentenceTransformerTrainer`, `CrossEncoderTrainer`) y la cuantización de embeddings. (NB 17) |

## Clustering y modelado de temas

| Término | Significado |
|---|---|
| **Clustering** (agrupamiento) | Agrupar elementos (aquí, textos convertidos en embeddings) de forma que los parecidos compartan grupo, sin etiquetas. Tres familias: por centroides (k-means), jerárquico (aglomerativo) y por densidad (DBSCAN, HDBSCAN). (NB 21) |
| **k-means** | Clustering que coloca $k$ centroides, asigna cada punto al más cercano y mueve cada centroide a la media de sus puntos hasta que nada cambia; k-means++ elige buenos centroides de partida. Es rápido, pero necesita $k$ por adelantado, supone clusters redondos y de tamaño parecido y asigna todos los puntos, también los atípicos. (NB 21: ARI 0,685 con la k = 77 verdadera en Banking77) |
| **HDBSCAN** | Clustering por densidad (Campello et al., 2013): los clusters son regiones densas separadas por otras poco densas, elegidos a partir de una jerarquía sobre todos los niveles de densidad. Encuentra solo el número de clusters y marca los puntos de las zonas poco densas como ruido (−1). Mando principal: `min_cluster_size`. (`sklearn.cluster.HDBSCAN`; NB 21: 73 clusters sin decirle k, 5 % de ruido) |
| **Curse of dimensionality** (maldición de la dimensionalidad) | Con cientos de dimensiones, las distancias se concentran: el vecino más cercano y el más lejano de un punto quedan a distancias parecidas, y los métodos basados en distancias y densidades pierden pie. Es el motivo para reducir dimensiones antes de agrupar. |
| **UMAP** | Uniform Manifold Approximation and Projection (McInnes et al., 2018): construye un grafo con los vecinos más cercanos de cada punto y busca una disposición en pocas dimensiones que lo conserve. Unas 5 dimensiones antes de agrupar; 2 solo para dibujar. (`umap-learn`; NB 21: ARI de k-means de 0,581 a 0,685 sobre UMAP 5-d) |
| **Topic modeling** (modelado de temas) | Encontrar los temas de una colección de documentos y describir cada uno, sin etiquetas. Hoy suele ser embeddings + clustering + un paso de descripción (BERTopic); antes, LDA. (NB 21) |
| **c-TF-IDF** | TF-IDF por clases: los documentos de cada cluster se concatenan y cada palabra se pondera por su frecuencia en el cluster por $\log(1 + A / f_w)$ ($A$: palabras medias por cluster, $f_w$: frecuencia total de la palabra), de modo que salen primero las palabras frecuentes en un cluster y raras en los demás. No necesita ningún modelo. (BERTopic; NB 21, escrito desde cero) |
| **BERTopic** | La librería y el pipeline (Grootendorst, 2022) que convirtieron en estándar el modelado de temas con embeddings: embeddings, reducción con UMAP, clustering con HDBSCAN y descripción con c-TF-IDF y, si se quiere, un LLM, con temas a lo largo del tiempo y fusión jerárquica. El NB 21 construye cada paso a mano. |
| **LDA (Latent Dirichlet Allocation)** | El modelo probabilístico de temas anterior (Blei et al., 2003): cada documento es una mezcla de temas y cada tema una distribución sobre palabras, ajustado con recuentos de bolsa de palabras. Flojo con textos cortos, y te deja listas de palabras que interpretar. No confundir con el análisis discriminante lineal. |
| **ARI (adjusted Rand index)** | Grado de acuerdo entre un clustering y unas etiquetas de referencia, calculado sobre pares de puntos (juntos o separados en ambos) y corregido por azar: 0 es aleatorio y 1 perfecto. (`adjusted_rand_score`; NB 21) |
| **NMI (normalized mutual information)** (información mutua normalizada) | Cuánto te dice el cluster de un punto sobre su etiqueta, normalizado a [0, 1]. Le afecta menos que al ARI cómo se reparten los puntos entre clusters. (`normalized_mutual_info_score`; NB 21: 0,873 para k-means con k = 77 sobre UMAP) |
| **Silhouette score** | Para cada punto, $(b - a) / \max(a, b)$, con $a$ su distancia media a su propio cluster y $b$ al cluster vecino más cercano, promediado sobre todos los puntos; no necesita etiquetas. Sirve para descartar valores malos de $k$, no para encontrar el "verdadero". (NB 21: elige k = 60 para 77 intenciones, y es plano entre 50 y 100) |
| **Cluster purity** (pureza de un cluster) | La proporción de puntos de un cluster que llevan su etiqueta mayoritaria. Se lee fácil cluster a cluster, pero premia tener muchos clusters diminutos, así que se da junto al ARI o la NMI. (NB 21: mediana del 91 %; el cluster más grande, un 32 %) |
| **Novelty / emerging-topic detection** (detección de novedades / temas emergentes) | Marcar las entradas que quedan lejos de todo lo que un sistema conoce (por ejemplo, con poca similitud con el centroide de cada intención conocida) y agrupar lo marcado, para que las necesidades nuevas aparezcan como grupos legibles que alguien revisa. (NB 21: precisión del 53 %, recall del 56 %, y las 7 intenciones apartadas salieron como clusters) |

## Modelos multimodales

| Término | Significado |
|---|---|
| **ViT (Vision Transformer)** | Un transformer que lee una imagen como una secuencia de parches (Dosovitskiy et al., 2021): los mismos bloques que para el texto, con embeddings de posición para la disposición en 2-D y un token de clase cuyo vector final representa la imagen entera. Una imagen de 224×224 con parches de 32×32 son 49 tokens más el de clase. Es el encoder de imagen de CLIP y de la mayoría de los VLMs. (NB 22: CLIP ViT-B/32) |
| **Patch embedding** (embedding de parches) | El equivalente en imagen del embedding de tokens: cada parche (de 16×16 o 32×32 píxeles) se aplana y se proyecta linealmente a un vector; en la práctica suele ser una convolución con el paso igual al tamaño del parche. |
| **CLIP** | Un encoder de imagen y otro de texto entrenados a la vez con 400 millones de pares (imagen, pie de foto) sacados de la web y una pérdida contrastiva (Radford et al., 2021), de modo que imágenes y textos comparten un mismo espacio de embeddings. Sirve para clasificar sin ejemplos, buscar imágenes, deduplicar y filtrar datos de entrenamiento. (NB 22: `openai/clip-vit-base-patch32`, 5,9 ms por imagen en la GPU) |
| **SigLIP** | CLIP cambiando la softmax sobre todo el batch por una pérdida sigmoide independiente para cada par (imagen, texto) (Zhai et al., 2023). Entrena mejor, también con batches más pequeños, y es el encoder de visión de muchos VLMs actuales. |
| **Zero-shot classification** (clasificación zero-shot) | Clasificar sin ningún ejemplo etiquetado de las clases. Con CLIP, cada clase se convierte en una frase ("a photo of a beagle"), se calculan los embeddings de las frases y cada imagen va a la más parecida. (NB 22: 86,3 % con 37 razas de mascotas) |
| **Prompt ensembling** (ensemble de prompts) | Calcular el embedding de varias plantillas por clase ("a photo of a {}", "a close-up photo of a {}"…) y promediarlos, lo que suaviza las manías de cada redacción; los autores de CLIP usaron 80 plantillas. (NB 22: 80,0 % con el nombre a secas, 85,2 % con una plantilla, 86,3 % con cinco) |
| **VLM** (modelo de visión y lenguaje) | Un modelo de lenguaje que recibe imágenes además de texto y genera texto: GPT-4o, Claude, Gemini, Qwen2.5-VL, Llama 3.2 Vision. Sirve para describir imágenes, responder preguntas sobre ellas y extraer datos de documentos y capturas de pantalla. (NB 22: `qwen2.5vl:3b`, 72,0 % en las razas frente al 83,3 % de CLIP con las mismas imágenes, a 1,45 s por imagen) |
| **Visual tokens / projector** (tokens visuales / proyector) | El diseño de VLM más extendido (LLaVA, Qwen-VL, InternVL): un encoder de visión convierte la imagen en vectores de parches, un **proyector** pequeño (una capa lineal o un MLP) los lleva al espacio de embeddings del LLM y entran en el prompt como tokens normales. Se pagan como el texto: tiempo de prefill, contexto y dinero. (NB 22: ~1.071 tokens de prompt por imagen) |
| **Cross-attention VLM** (VLM con cross-attention) | El otro diseño (Flamingo, Llama 3.2 Vision): dentro de las capas del LLM se añaden bloques de cross-attention que leen las características de la imagen, igual que el decoder de un encoder-decoder lee al encoder, así que las imágenes no ocupan contexto. |
| **Dynamic resolution** (resolución dinámica) | Dejar que el número de tokens visuales crezca con los píxeles de la imagen en vez de redimensionar todas a un tamaño fijo. Qwen2.5-VL usa un token por cada zona de 28×28. La pila de serving puede no hacerlo: en el NB 22, Ollama dio ~1.080 tokens por imagen fuera cual fuera su tamaño, y reducirla antes a 224 px bajó el acierto al 55 %. |
| **Typographic attack** (ataque tipográfico) | Texto escrito sobre una imagen que se impone a lo que la imagen muestra: una manzana con la etiqueta "iPod" se clasifica como un iPod (Goh et al., 2021). Para un VLM es una inyección de prompt a través de los píxeles. (NB 22: con una raza equivocada escrita en una esquina, CLIP la sigue el 8 % de las veces y `qwen2.5vl:3b` el 72 %) |
| **Document AI / OCR** | Extraer texto y campos de documentos: facturas, tickets, formularios, capturas de pantalla. El OCR (Tesseract, PaddleOCR, OCR en la nube) convierte píxeles en texto; los pipelines de producción lo combinan con modelos de maquetación y VLMs, o lo sustituyen por ellos, y validan los campos con reglas de negocio. (NB 22: un VLM con un esquema JSON extrae los cinco campos de 40 facturas sintéticas, limpias y degradadas, en 2,3 s por documento; las facturas son demasiado fáciles para concluir más) |

## Aplicaciones: LangChain y RAG

| Término | Significado |
|---|---|
| **RAG (Retrieval-Augmented Generation)** | Recuperar fragmentos relevantes de tus documentos y pasarlos como contexto al LLM. (NB 18, `scripts/rag_demo.py`) |
| **Chunking** | Partir documentos en fragmentos (con solapamiento) antes de indexarlos, p. ej. con el `RecursiveCharacterTextSplitter` de LangChain. |
| **Runnable** | La interfaz común de LangChain: cada componente (prompt, modelo, parser, retriever, función envuelta en `RunnableLambda`) tiene `invoke`, `batch` y `stream` (y sus versiones asíncronas), así que todos se componen y se trazan igual. |
| **LCEL (LangChain Expression Language)** | Componer Runnables con `\|` (`prompt \| llm \| StrOutputParser()`). `RunnableParallel` ejecuta ramas sobre la misma entrada, `RunnablePassthrough` la deja pasar sin cambios y `.assign(...)` añade claves a un diccionario. |
| **Vector store** | Base de datos de embeddings que devuelve los vecinos más cercanos de un vector de consulta: `FAISS` e `InMemoryVectorStore` en el curso; pgvector, Qdrant o Weaviate en producción. |
| **Retriever** | Un Runnable que convierte una consulta en una lista de `Document`. `vector_store.as_retriever(search_kwargs={"k": 4})`, `BM25Retriever`, `EnsembleRetriever` y `MultiQueryRetriever` son todos retrievers. |
| **Dense retrieval / BM25 / hybrid** | Búsqueda por embeddings (semántica), por términos (léxica) o combinada. |
| **RRF (Reciprocal Rank Fusion)** | Fusionar rankings sumando `1/(60 + posición)`. Solo usa posiciones, no puntuaciones, así que no necesita calibración. Con pesos iguales, un recuperador mucho más flojo puede hundir a uno bueno (NB 17: BM25 + bi-encoder ajustado da 0,735 de nDCG@10, frente al 0,762 del bi-encoder solo). |
| **EnsembleRetriever** | Retriever de LangChain (en `langchain_classic` en LangChain 1.x) que ejecuta varios retrievers y fusiona sus rankings con **RRF ponderado**. El curso combina BM25 y FAISS con pesos 0,5 / 0,5. |
| **Reranker / cross-encoder** | Segunda etapa, más cara, que vuelve a puntuar los mejores candidatos de un recuperador rápido leyendo consulta y documento juntos. Un LLM puede hacer ese papel, pero no siempre compensa: en recomendación, un LLM pequeño reordenando la lista de un modelo colaborativo la empeoró (v2 del NB 23), y la versión actual usa un ranker LambdaMART. En el NB 17, dos cross-encoders generales no mejoraron a un bi-encoder ajustado en SciFact (ms-marco-MiniLM 0,692 y bge-reranker-base 0,731 en el mejor caso, frente a 0,735 sin reranker). Ver **cross-encoder**. |
| **recall@k / hit@k / MRR / nDCG** | Métricas de recuperación: ¿está el documento correcto en el top-k?, inverso de la posición del primero correcto, y ganancia acumulada con descuento por posición. **recall@k** es la fracción de los documentos relevantes de una consulta que aparecen en el top k (hit@k cuando solo hay uno); **nDCG@k** da a un documento relevante en la posición r una ganancia de `1/log2(r+1)` y divide la suma por la mejor puntuación posible para esa consulta, así que premia poner arriba los relevantes. nDCG@10 es la métrica principal de BEIR y de la parte de recuperación de MTEB; recall@100 es el material con el que puede trabajar un reranker. `rag_demo.py` las calcula a nivel de fichero y a nivel de *evidencia* (¿el chunk contiene de verdad la respuesta?). (NB 18, NB 23, NB 17) |
| **Faithfulness / groundedness** | Si la respuesta está respaldada por el contexto recuperado (y no inventada). |
| **RAGAS** | Librería para evaluar RAG con un LLM como juez. Sus cuatro métricas principales: **faithfulness** (¿las afirmaciones de la respuesta están respaldadas por el contexto recuperado?), **answer relevancy** (¿la respuesta contesta a la pregunta? se mide generando preguntas a partir de la respuesta y comparando embeddings), **context precision** (¿los chunks relevantes salen arriba?) y **context recall** (¿el contexto recuperado cubre la respuesta de referencia?). Las dos últimas necesitan una respuesta de referencia. (NB 18, NB 19, `rag_demo.py --ragas`) |
| **LLM-as-judge** | Usar un LLM para puntuar o comparar respuestas (pairwise, con rúbrica). Hay que controlar sesgos de posición y longitud, y validar al juez antes de fiarse de él. |
| **Judge strength** (fuerza del juez) | Lo capaz que es el juez respecto al sistema que evalúa. Un juez débil no solo añade ruido: puede inventar diferencias entre sistemas. En el NB 18, el 3B juzgándose a sí mismo informaba de faithfulness 0,38 → 0,54 entre recuperación densa e híbrida; con `qwen2.5:7b` como juez, 0,87 en ambas. Regla: un juez más fuerte que el sistema, fijo mientras se comparan versiones (`config.judge_model()`, `JUDGE_MODEL`). |
| **Structured output** | Forzar salidas que cumplan un esquema. En LangChain, `llm.with_structured_output(ModeloPydantic)` usa el tool calling o el modo JSON del proveedor y devuelve un objeto validado. (NB 16) |
| **Constrained decoding** (decodificación restringida) | El servidor convierte el esquema en una gramática y, en cada paso, enmascara los tokens que la romperían, así que la salida siempre es válida (en Ollama, `method="json_schema"`). Garantiza la forma, no el contenido. Con un enum grande es imprescindible: en el NB 06, con 77 intenciones, `function_calling` dio 181 salidas inválidas de 231 y `json_schema` ninguna; en el NB 16, con un esquema pequeño, function calling fue el método más fiable. (NB 16, NB 19, NB 06) |
| **Tool calling / function calling** | El modelo devuelve una llamada estructurada (`nombre` + argumentos JSON) que tu código ejecuta. En LangChain una herramienta es una función decorada con `@tool`, y `llm.bind_tools(...)` se la muestra al modelo. (NB 16) |
| **Agent loop** | Bucle modelo → herramienta → observación → modelo, con límite de pasos. `create_agent` de `langchain.agents` lo construye sobre LangGraph. |
| **Middleware (agentes de LangChain)** | Ganchos que envuelven las llamadas del agente al modelo y a las herramientas para añadir comportamiento sin reescribir el bucle: `ModelCallLimitMiddleware` / `ToolCallLimitMiddleware` (presupuestos), `HumanInTheLoopMiddleware` (aprobación antes de ejecutar una herramienta), `ToolErrorMiddleware` (convertir excepciones de herramientas en mensajes), `SummarizationMiddleware` (comprimir historiales largos), o tu propio `AgentMiddleware`. (NB 16, 25, 26) |
| **Human-in-the-loop / confirmation gate** | Pedir aprobación antes de ejecutar acciones con efectos (pagos, borrados, envíos). |
| **Prompt injection** | Texto malicioso dentro de los datos (una web, un email, un documento, el resultado de una herramienta) que intenta dar órdenes al modelo. (NB 16, 19, 25, 26) |
| **Indirect prompt injection** (inyección de prompts indirecta) | La instrucción llega dentro del contenido que el modelo lee mientras trabaja (un fichero, una web, el resultado de una herramienta), no del usuario. Los prompts y los filtros bajan su tasa de éxito; el aislamiento (sin secretos y sin forma de sacar datos) acota el daño cuando funciona. Para un agente de programación, el propio repositorio es ese contenido: READMEs, comentarios, issues, código de las dependencias. (NB 25, 27) |
| **Semantic cache** | Reutilizar respuestas de preguntas *parecidas* (por similitud de embeddings). Riesgo: *false hits*. (NB 19) |

## Optimización de prompts (DSPy)

| Término | Significado |
|---|---|
| **DSPy** | Un framework de Stanford NLP que trata los prompts como parámetros de un programa: declaras cada paso con un LLM como una signature, compones los pasos en módulos y dejas que un optimizador elija las instrucciones y los ejemplos que maximizan tu métrica sobre tus datos. La versión 3.5 trae su propio cliente HTTP (`engine="lm15"`), así que puede hablar con el endpoint compatible con OpenAI de Ollama sin litellm. (NB 20) |
| **Signature (DSPy)** | El contrato declarado de un paso con LLM: campos de entrada y de salida con tipo, más un docstring como descripción de la tarea, p. ej. `message: str -> intent: Literal[...]`. Dice *qué* hace el paso y nada de la redacción; el prompt lo escribe el adaptador. (NB 20) |
| **Module** (módulo, DSPy) | Lo que convierte una signature en llamadas: `dspy.Predict` (una llamada), `dspy.ChainOfThought` (añade una salida `reasoning` antes de la respuesta), `ReAct`, o tu propio `dspy.Module` con un método `forward`. Los módulos se componen como capas de PyTorch. (NB 20) |
| **Adapter** (adaptador, DSPy) | La capa que convierte una signature, sus demos y las entradas en los mensajes de verdad, y parsea la respuesta de vuelta a campos con tipo. El `ChatAdapter` por defecto escribe los campos, los tipos y los valores permitidos en el mensaje de sistema y pide la respuesta en campos delimitados (`[[ ## intent ## ]]`); en el NB 20 son ~4.100 caracteres de prompt de sistema para 77 etiquetas, y ninguna de las 231 respuestas falló al parsearse. |
| **Few-shot / demos** | Ejemplos de entrada y salida que se ponen en el prompt (en DSPy, como turnos anteriores) para que el modelo vea qué se quiere. Importa más cuáles que cuántos: en el NB 20, 16 ejemplos al azar bajan el acierto de 0,558 a 0,433, porque con 77 clases cubren como mucho 16 y arrastran al modelo hacia ellas. |
| **kNN few-shot** (few-shot por vecinos) | Elegir las demos *para cada entrada*: codificar una vez el conjunto etiquetado y poner en el prompt de cada entrada nueva los k ejemplos de entrenamiento más cercanos (Liu et al., 2021; `dspy.KNNFewShot`). En el NB 20, 16 demos por vecinos suben a `qwen2.5:3b` a 0,870 en Banking77, aunque un simple voto de los 8 vecinos, sin LLM, llega a 0,913. Durante la optimización hay que sacar a la propia entrada de sus demos. |
| **Bootstrapped demos** (demos bootstrapped) | Demos que se construyen ejecutando el programa sobre entradas de entrenamiento y quedándose con las trazas cuya salida pasa la métrica, así que pueden incluir pasos intermedios (razonamiento, subllamadas) que nadie escribió a mano. `BootstrapFewShotWithRandomSearch` prueba varios de esos conjuntos y se queda con el mejor en validación; en el NB 20, el mejor de 9 candidatos fue el programa sin optimizar. |
| **MIPROv2** | Un optimizador de DSPy que ajusta la instrucción **y** las demos (Opsahl-Ong et al., 2024): un *prompt model* propone instrucciones candidatas a partir de un resumen de los datos y del programa, y una optimización bayesiana (el TPE de Optuna) elige la combinación de instrucción y conjunto de demos, puntuada sobre minilotes. En el NB 20 (`qwen2.5:7b` proponiendo para el 3B) se quedó con la instrucción original y sin demos: 0,554 frente a 0,558. |
| **GEPA** | Un optimizador de prompts reflexivo (Agrawal et al., 2025): ejecuta el programa, le enseña a un *modelo de reflexión* los fallos con el feedback en texto de la métrica y hace evolucionar la instrucción, con un frente de Pareto de candidatas que ganan en ejemplos distintos. En el NB 20 llegó al 59,7 % en validación y a 0,554 en test: su instrucción larga memorizó los fallos con los que se escribió. |
| **Prompt optimizer** (optimizador de prompts) | Cualquier procedimiento que busca prompts (instrucciones, demos o las dos cosas) para maximizar una métrica sobre datos etiquetados, y que se paga una vez, al "compilar". Se sobreajusta a un set de validación pequeño, solo puede buscar en el espacio que le das, y lo que produce son datos (JSON) que se versionan y se vuelven a optimizar cuando cambian el modelo, los datos o la métrica. (NB 20) |

## Sistemas de recomendación

| Término | Significado |
|---|---|
| **Recommendation funnel** (embudo de recomendación) | La arquitectura en etapas de un recomendador industrial: **generación de candidatos** (de millones a cientos, barata, se mide por recall), **ranking** (de cientos a decenas, con muchas features, se mide por nDCG) y **re-ranking** (reglas, diversidad, exploración, explicaciones). (NB 23) |
| **Candidate generation / retrieval** (generación de candidatos) | La primera etapa del embudo: varias fuentes baratas (modelo secuencial, two-tower + ANN, co-ocurrencia, contenido, populares) cuya **unión** forma el conjunto de candidatos. Su recall es el techo del ranker: lo que no se recupera no se puede ordenar. (NB 23) |
| **Sequential recommender (SASRec)** (recomendador secuencial) | Recomendación como "predicción del siguiente ítem" con un transformer causal sobre el historial del usuario; el vocabulario es el catálogo. Se entrena mejor con la softmax completa que con negativos muestreados; a escala de millones, **softmax muestreada con corrección logQ** (restar a cada logit el log de su probabilidad de muestreo). (NB 23) |
| **Two-tower model** (modelo de dos torres) | Dos redes que llevan usuario e ítem al mismo espacio; la puntuación es su producto escalar. Como la torre de ítems no depende del usuario, sus vectores se precalculan y se sirven con un índice ANN. Con **id dropout** (ocultar el id al azar en el entrenamiento) aprende a colocar ítems nuevos desde su contenido. (NB 23) |
| **ANN / HNSW** (búsqueda aproximada de vecinos) | *Approximate nearest neighbours*: índices que devuelven casi los mismos vecinos que la búsqueda exacta en mucho menos tiempo. HNSW es el de grafo jerárquico (FAISS, ScaNN, bases vectoriales); su recall frente a la búsqueda exacta es un parámetro de calidad propio. (NB 18, 23) |
| **Learning to rank** (aprendizaje de ranking) | Entrenar un modelo para ordenar: **pointwise** (predecir cada etiqueta por separado), **pairwise** (preferir el positivo a cada negativo, RankNet) o **listwise** (optimizar la calidad de la lista entera). (NB 23) |
| **LambdaMART** | Árboles con gradient boosting cuyos gradientes son los de RankNet por pares, ponderados por cuánto cambiaría el nDCG al intercambiar los dos ítems. El ranker industrial por defecto; en LightGBM, `objective="lambdarank"`. Solo aporta sobre una primera etapa fuerte si tiene muchas consultas de un periodo posterior y features que esa etapa no ve. (NB 23) |
| **Cold start** (arranque en frío) | Recomendar ítems (o a usuarios) sin historial de interacciones. Lo colaborativo no puede: la fila del ítem nunca se entrenó. Se resuelve con contenido (texto, metadatos) para colocarlo y exploración para darle exposición. (NB 23) |
| **Exploration slot / bandit** (ranura de exploración) | Reservar posiciones de la lista para ítems nuevos o inciertos, para aprender cuánto valen (dilema exploración/explotación). Los *bandits* ($\varepsilon$-greedy, UCB, Thompson sampling, contextuales como LinUCB) lo deciden de forma adaptativa; una ranura fija es la versión mínima medible offline. (NB 23) |
| **MMR (Maximal Marginal Relevance)** (relevancia marginal máxima) | Construir la lista de forma voraz eligiendo cada vez $\lambda \cdot$ relevancia $- (1-\lambda) \cdot$ máxima similitud con lo ya elegido. Con $\lambda = 1$ es el ranking puro; más bajo, más diversidad. (NB 23) |
| **Intra-list diversity** (diversidad intra-lista) | Uno menos la similitud media entre los pares de ítems de una lista (en el NB 23, Jaccard de géneros). Offline solo puede parecer neutra o peor para la precisión; su beneficio se mide online. La **calibración** (Steck, 2018) pide además que la mezcla de géneros de la lista se parezca a la del historial. |
| **Leave-last-out / leave-last-two** (dejar fuera el último) | Partición temporal por usuario: el último evento es el objetivo de test (y el penúltimo, el de validación); todo lo anterior es historial. Una partición aleatoria filtraría el futuro. (`recsys.temporal_split`, NB 23) |
| **Full ranking vs sampled metrics** (ranking completo frente a métricas muestreadas) | Ordenar el objetivo contra **todo** el catálogo o contra unos 100 negativos aleatorios. Las muestreadas inflan los números y pueden invertir qué modelo parece mejor (Krichene y Rendle, 2020). (`recsys.target_ranks`, NB 23) |

## Drift y aprendizaje online

| Término | Significado |
|---|---|
| **Data drift / distribution shift** (drift de datos) | Cualquier cambio entre los datos con los que se entrenó un modelo y los que ve ahora. Degrada la calidad sin hacer ruido: nada falla, los resultados simplemente empeoran. Debajo, los tres tipos. (NB 24) |
| **Covariate shift** (cambio de covariables) | Cambia la distribución de las entradas $P(x)$ y $P(y \mid x)$ se mantiene: usuarios de un país nuevo, un tipo nuevo de pregunta. |
| **Label / prior shift** (cambio en las etiquetas) | Cambia la distribución de los resultados $P(y)$: un taquillazo se lleva buena parte de las visualizaciones, una oleada de fraude sube su proporción. |
| **Concept drift** | Cambia la relación $P(y \mid x)$: la misma entrada lleva ahora a otro resultado. Puede ocurrir sin ningún cambio visible en las entradas. (NB 24: un recomendador de co-visitación envejeció de un hit@10 de 0,184 a 0,160 mientras el PSI de sus entradas seguía en 0,01–0,03) |
| **Feedback loop** (bucle de retroalimentación) | Un modelo moldea los datos con los que luego se entrenará: un recomendador decide qué ven los usuarios y, por tanto, en qué hacen clic. Estrecha la exposición e infla el acierto aparente, salvo que la exploración lo rompa. (NB 23, NB 24) |
| **Continual / online learning** (aprendizaje continuo / online) | Actualizar un modelo a medida que llegan los datos en vez de una sola vez: con cada evento o mini-batch (online, con SGD o con recuentos que decaen con el tiempo) o por incrementos periódicos. Es fresco, pero los datos malos entran en producción al instante, y las redes neuronales pueden olvidar lo que sabían (olvido catastrófico). (NB 24: popularidad con recuentos que se reducen a la mitad cada 7 días) |
| **Warm start** | Seguir entrenando el último modelo con los datos nuevos en lugar de empezar de cero: más barato, y lo normal con modelos grandes. |
| **Prequential evaluation** (evaluación precuencial) | "Test-then-train" sobre un flujo: cada evento se predice primero con el modelo actual y solo después se usa para aprender, así que todas las predicciones son fuera de muestra y la puntuación a lo largo del tiempo enseña cómo envejece el modelo. (NB 24) |
| **PSI (population stability index)** | $\sum_b (p_b - q_b)\ln(p_b / q_b)$ entre una distribución de referencia $q$ y la actual $p$ sobre unos intervalos: una divergencia KL simetrizada. Regla práctica: < 0,1 estable, 0,1–0,25 moderado, > 0,25 cambio importante. (NB 24: 0,01–0,03 todas las semanas, así que un disparador de reentrenamiento con PSI > 0,25 no saltó nunca) |
| **KS test (Kolmogorov-Smirnov)** (test KS) | Test de dos muestras sobre una variable numérica: el estadístico es la mayor diferencia entre las dos funciones de distribución empíricas, con un p-valor. Es la comprobación de drift habitual variable a variable, junto al chi cuadrado para categorías y las divergencias KL y de Jensen-Shannon. |
| **MMD (maximum mean discrepancy)** | Una distancia entre dos muestras a través de un kernel, $\mathbb{E}[k(x,x')] + \mathbb{E}[k(y,y')] - 2\,\mathbb{E}[k(x,y)]$ (Gretton et al., 2012), con un p-valor sacado de un test de permutaciones. Funciona con embeddings, donde los tests variable a variable no sirven. (NB 24: detectó siempre un cambio del 40 % en las intenciones de Banking77, y uno del 20 % el 25 % de las veces) |
| **Classifier two-sample test** (test de dos muestras con clasificador) | Entrenar un clasificador para distinguir los datos de referencia de los actuales: un AUC con validación cruzada claramente por encima de 0,5 indica que son distintos, y lo que acierta el clasificador enseña dónde (Lopez-Paz y Oquab, 2017). (NB 24: AUC de 0,48–0,50 hasta un cambio del 20 %, 0,554 con el 40 %) |
| **Canary release** (despliegue canary) | Desplegar primero un modelo nuevo para una parte pequeña del tráfico, vigilar sus métricas frente al actual y ampliarlo o volver atrás. Suele ir seguido de un test A/B. |

## Agentes y LangGraph

| Término | Significado |
|---|---|
| **Workflow vs agent** | En un *workflow* el código fija el flujo de control y el LLM rellena los pasos; en un agente es el LLM quien elige el siguiente paso, en bucle. Empieza por lo más simple que funcione. (NB 25) |
| **StateGraph** | El constructor de LangGraph para un grafo cuyos nodos leen y actualizan un **estado** compartido y tipado (un `TypedDict`, o `MessagesState` para chat). `builder.compile()` lo convierte en un Runnable. (NB 25) |
| **Node** | Una función `estado -> actualización parcial del estado` en un grafo de LangGraph: una llamada al LLM, una recuperación, una herramienta, Python normal. |
| **Edge / conditional edge** | Una arista fija el siguiente nodo (`add_edge("a", "b")`, desde `START` o hacia `END`). Una arista condicional (`add_conditional_edges`) llama a una función del estado que devuelve el nombre del siguiente nodo: enrutado, bucles, reintentos. |
| **Checkpointer** | Guarda el estado del grafo tras cada paso (`InMemorySaver` en el curso; SQLite o Postgres en producción). Da al grafo memoria a corto plazo, le permite reanudar tras un fallo o una pausa y habilita el *time travel*. |
| **Thread (`thread_id`)** | La clave bajo la que un checkpointer guarda una conversación: `config={"configurable": {"thread_id": "..."}}`. Mismo hilo = misma memoria. |
| **Store** | La memoria a largo plazo de LangGraph: un almacén clave-valor organizado en espacios de nombres (p. ej. `("users", user_id)`), compartido entre hilos, con búsqueda semántica opcional si se le da un modelo de embeddings (`InMemoryStore`). |
| **Interrupt** | `interrupt(valor)` pausa un grafo dentro de un nodo y devuelve `valor` a quien lo llamó; la ejecución se reanuda con `Command(resume=...)`. Necesita un checkpointer. Es la base del human-in-the-loop en LangGraph. |
| **`recursion_limit` / agent budget** | Límites duros de una ejecución de un agente: el `recursion_limit` de LangGraph limita el número de pasos, y los middlewares de límite de llamadas limitan las llamadas al modelo y a las herramientas. Al alcanzar uno, la ejecución se detiene en lugar de dar vueltas. |
| **Plan-and-execute** | Patrón que primero pide al LLM un plan numerado, luego ejecuta cada paso con un agente con herramientas y por último sintetiza la respuesta. Se puede inspeccionar y aprobar. (NB 25) |
| **Reflection / verifier** | Bucle borrador → verificar → revisar. El verificador comprueba el borrador y devuelve feedback; el código (tests, validadores de esquema) es mucho más fiable que un crítico LLM. (NB 25) |
| **Router** (enrutador) | Un nodo que envía cada petición a un especialista (un subagente o una cadena), mediante una clasificación del LLM o por similitud de embeddings. Es un clasificador y se evalúa como tal. (NB 19, 25) |
| **Supervisor / agents as tools / orchestrator-workers** | Un diseño multi-agente en el que un agente supervisor llama a agentes especialistas como si fueran herramientas, lee sus respuestas, puede volver a llamar y redacta la respuesta final. El control siempre vuelve al supervisor, y su coste incluye las llamadas al modelo de cada trabajador. (NB 25) |
| **Handoff** (traspaso) | Un diseño multi-agente en el que el agente activo traspasa la conversación a otro agente, que toma el relevo; responde el que termina. Lo que ve el agente que recibe (la ingeniería de contexto en el traspaso) decide si funciona. (NB 25) |
| **Swarm** | Un equipo de agentes conectados solo por handoffs, sin supervisor central (Swarm y el Agents SDK de OpenAI, `langgraph-swarm`). |
| **`Command` / `graph=Command.PARENT`** | Un valor de retorno de LangGraph que actualiza el estado y nombra el siguiente nodo de una vez (`Command(goto="billing", update=...)`); también reanuda una interrupción (`Command(resume=...)`). Con `graph=Command.PARENT`, devuelto desde una herramienta dentro de un agente, el salto se da en el grafo padre: así pasa el control de un agente a otro en un handoff. (NB 25) |
| **Short-term / long-term memory** | La conversación del hilo actual (checkpointer, quizá resumida) frente a los hechos que sobreviven entre hilos (store, recuperados por similitud). |
| **Trajectory evaluation** | Puntuar el camino que siguió un agente (qué herramientas, en qué orden, cuántas llamadas de más), no solo su respuesta final. (NB 16) |
| **Code execution / code interpreter** (ejecución de código) | Dejar que el modelo escriba un programa y ejecutarlo, en lugar de llamar a una herramienta fija o calcular de cabeza. PAL y Program of Thoughts (2022) pasaron a código la aritmética del razonamiento; CodeAct (2024) hace del código el formato de las acciones del agente. (NB 25) |
| **Execution feedback** (feedback de ejecución) | Devolver al modelo el resultado de ejecutar su código (la salida, el traceback, "no se imprimió nada") para que lo arregle y vuelva a intentarlo. Arregla errores, no un código que se ejecuta y calcula otra cosa. (NB 25) |
| **Agent-computer interface, ACI** (interfaz agente-ordenador) | Diseñar las herramientas pensando en cómo lee y escribe un modelo, no una persona: salida concisa, mensajes explícitos para errores y resultados vacíos, salvaguardas como un editor que rechaza ediciones inválidas (SWE-agent, Yang et al., 2024). (NB 25) |
| **Sandbox** | Un entorno aislado para ejecutar código no fiable (aquí, el que escribe el modelo): sin secretos, sin red, con su propio sistema de ficheros, timeout y cuotas de recursos. Su fuerza depende de la capa que lo impone: un proceso, un contenedor, un kernel en espacio de usuario o una VM. (NB 25, 27) |
| **Audit hook (PEP 578)** | Una función de Python registrada con `sys.addaudithook` que ve los eventos del intérprete (`open`, sockets, subprocesos, cargas de `ctypes`) y puede vetarlos lanzando una excepción. Útil para registrar y como cable trampa, pero no es una frontera de seguridad: el código nativo se lo salta. (NB 25) |
| **gVisor / microVM (Firecracker)** | Aislamiento más fuerte que un contenedor, que comparte el kernel del host. gVisor es un kernel en espacio de usuario que intercepta las llamadas al sistema del sandbox; una microVM (Firecracker, detrás de AWS Lambda y de E2B) es una máquina virtual mínima con su propio kernel que arranca en una fracción de segundo. |

## Harnesses de agentes

| Término | Significado |
|---|---|
| **Agent harness** (harness de agentes) | El programa que rodea a un modelo y lo convierte en un agente: le da una forma de actuar (una shell, edición de ficheros, herramientas, servidores MCP), ejecuta el bucle pensar → actuar → observar, decide qué se puede ejecutar sin preguntar, aísla lo que se ejecuta, mantiene el historial dentro de la ventana de contexto, carga las instrucciones del proyecto y registra cada paso. Claude Code, Codex CLI, Gemini CLI, opencode y OpenHands son harnesses; mini-swe-agent es uno mínimo. (NB 27) |
| **mini-swe-agent** | El harness mínimo del equipo de SWE-bench (MIT): un comando bash por turno, extraído de un único bloque de código, un subproceso nuevo en cada paso y un historial lineal. Lo bastante pequeño para leerlo en una tarde y programable para evaluaciones. En el NB 27 se ejecuta desde su propio `.venv-harness` a través de `scripts/harness_run.py`. |
| **SWE-bench** | Un benchmark de issues reales de GitHub de repositorios de Python (Jimenez et al., 2024): el agente recibe la issue y el repositorio, y su parche se juzga con los tests del propio proyecto, que nunca ve. *SWE-bench Verified* es el subconjunto revisado por personas sobre el que se publican casi todos los resultados. El NB 27 copia su forma de puntuar en 16 tareas pequeñas. |
| **Trajectory** (trayectoria) | El registro completo de una ejecución de un agente: cada mensaje del modelo, cada comando y cada observación, en orden, más el estado de salida. En mini-swe-agent la trayectoria *es* el prompt, y se guarda en JSON. Es el registro para depurar un agente y los datos de entrenamiento del siguiente. (NB 27) |
| **Step limit / `LimitsExceeded`** (límite de pasos) | Un tope al número de llamadas al modelo en una ejecución; al alcanzarlo, mini-swe-agent termina la ejecución con el estado `LimitsExceeded` (con un tope de coste, el mismo estado; con un tope de tiempo, `TimeExceeded`). En el NB 27 de la v2.8, con 15 pasos, así terminaron 4 ejecuciones del 3B y 6 del 7B; Claude Haiku 5.5 necesitó 3,5 pasos de media, lejos del límite. |
| **Format error** (error de formato) | Una respuesta que el harness no consigue convertir en una acción (sin bloque de comando, o con más de uno). mini-swe-agent le devuelve el error al modelo como siguiente observación ("provide EXACTLY ONE action") y se para tras 3 seguidos (`RepeatedFormatError`). Una respuesta cortada por un presupuesto de tokens demasiado pequeño cuenta como uno: en el NB 27, con 1.024 tokens por respuesta, la tarea 16 falló así. Las llamadas a herramientas nativas eliminan el bloque de código, y con él este error. (NB 27) |
| **Hidden tests** (tests ocultos) | Tests que deciden si un agente resolvió una tarea pero que se copian solo al terminar la ejecución, así que el agente no puede verlos ni editarlos. Es como puntúa SWE-bench, y la única comprobación justa para un agente que puede cambiar cualquier fichero. (NB 27) |
| **False "done"** (falso "terminado") | Una ejecución en la que el agente da la tarea por acabada (en mini-swe-agent, estado de salida `Submitted`) mientras los tests ocultos fallan. En el NB 27 de la v2.8, con modelos locales de 3–8B, 11 de 30 ejecuciones; Claude Haiku 5.5 no tuvo ninguna. Lo que el propio agente dice de su éxito es la señal menos fiable del bucle. |
| **Repeated-action detection** (detección de acciones repetidas) | Una salvaguarda del harness que se da cuenta de que el modelo manda el mismo comando una y otra vez, y le inyecta una pista o para la ejecución. mini-swe-agent no la tiene: en el NB 27 de la v2.8 el 3B mandó un mismo `sed` roto cinco veces y se gastó en él su presupuesto de pasos. La función `loop` del perfil moderno del harness la añade (un aviso tras tres llamadas idénticas con el mismo resultado). |
| **Context compaction** (compactación del contexto) | Mantener una ejecución larga de un agente dentro de la ventana de contexto resumiendo los turnos antiguos, recortando la salida de las herramientas o recuperando solo lo necesario. Los harnesses completos compactan solos; el historial de mini-swe-agent simplemente crece. |
| **Project memory, `AGENTS.md` / `CLAUDE.md`** (memoria del proyecto) | Un fichero del repositorio que el harness carga al empezar con lo que el código no dice: cómo compilar y ejecutar los tests, las convenciones, dónde va cada cosa y qué no hacer nunca. `AGENTS.md` lo leen Codex CLI, opencode, Cursor y muchos otros; Claude Code lee `CLAUDE.md` y Gemini CLI `GEMINI.md`. En el NB 27 de la v2.8 llevó al 3B del 0 % al 33 % en tareas que solo dependen de convenciones; Claude Haiku 5.5 las resolvió al 100 % con y sin él en el prompt, porque abrió `AGENTS.md` por su cuenta en 9 de 9 ejecuciones. Mantenlo corto y respalda cada regla con un test. |
| **Permission policy / deny list** (política de permisos / lista de denegación) | Las reglas que deciden qué puede hacer un agente sin preguntar: permitir / preguntar / denegar por herramienta (opencode, Claude Code), políticas de ejecución y modos de aprobación (Codex CLI), o confirmar cada comando. Una lista de denegación rechaza los comandos que coinciden con unos patrones (red, `git push`, lectura de secretos, `sudo`, salir de la carpeta de la tarea, buscar por todo el disco) y le devuelve el rechazo al modelo como observación. Una lista de patrones es fácil de esquivar, así que va encima de un sandbox, no en su lugar. (NB 27, `scripts/harness_run.py`) |
| **Scrubbed environment** (entorno limpio) | Ejecutar los comandos del agente solo con una lista blanca de variables de entorno (`PATH`, `TEMP`, `HOME`...), para que las claves de API y los tokens del proceso padre no le lleguen nunca. (NB 25, 27) |
| **Observation masking** (enmascarado de observaciones) | Una forma barata de compactar el contexto de un agente: las salidas de herramientas más antiguas que las últimas se sustituyen en el prompt por un marcador de una línea, mientras la trayectoria en disco lo guarda todo (Lindenbauer et al., 2025, *The Complexity Trap*). La opción `mask` del perfil moderno del harness conserva las 6 últimas. Edita el historial, así que no se puede usar con modelos que exigen uno de solo añadir (ver *Preserved thinking*): el NB 27 la omite con Claude. (`scripts/harness_modern.py`, NB 27) |
| **Workspace context** (contexto del espacio de trabajo) | Lo que un harness le cuenta al modelo de su entorno antes del primer paso: la carpeta de trabajo, los ficheros que hay en ella y cómo ejecutar el código y los tests (el bloque de entorno de Claude Code, el contexto del workspace de Codex). En el NB 27, sin él algunas tareas empezaban con `find /` (7 pasos, ~75 s); con él, 4 pasos y ~7 s. (`scripts/harness_run.py`) |
| **Verification gate / stop hook** (puerta de verificación) | Una comprobación del harness que rechaza el "terminado" del agente mientras no haya pruebas de que el trabajo está bien, por ejemplo mientras fallen los tests visibles o si no se ejecutó código tras la última edición. Hay que probarla a ella también: en el NB 27 la primera versión exigía código de salida 0 y rechazó 7 entregas en dos ejecuciones, y las 5 que se revisaron eran correctas (`pytest` con salida 5, "no tests ran"; un `grep` final con salida 1). Una puerta con falsos positivos cuesta pasos y no enseña nada. (`scripts/harness_modern.py`) |
| **Preserved thinking** (pensamiento preservado) | Un requisito de los modelos actuales de Claude con pensamiento extendido: el historial anterior a cada bloque de pensamiento tiene que llegar a la API sin cambios, o la llamada falla (HTTP 400, "Invalid signature in thinking block"). El cliente tiene que mantener la conversación de solo añadir y dejar la compactación a la edición de contexto del lado del servidor del proveedor; por eso el NB 27 omite el enmascarado de observaciones en el cliente con los modelos `anthropic/` (la trayectoria registra `mask_skipped`). |

## LLMOps y LangSmith

| Término | Significado |
|---|---|
| **LangSmith** | La plataforma de LangChain para trazar, monitorizar y evaluar aplicaciones LLM. Con `LANGSMITH_TRACING=true` y una clave de API, se registra cada llamada de LangChain / LangGraph y cada función decorada con `@traceable`. Opcional en el curso. (NB 28) |
| **Run** | Una unidad de trabajo registrada por LangSmith: una llamada al LLM, un retriever, una herramienta, una cadena, un nodo de un grafo. Cada run tiene entradas, salidas, tiempos, tokens, errores, etiquetas, metadatos y un run padre. |
| **Trace** | El árbol de runs que produce una petición de nivel superior, desde el run raíz hasta cada llamada anidada. Es el árbol de spans de OpenTelemetry. |
| **Project** | El contenedor de LangSmith al que se envían las trazas (`LANGSMITH_PROJECT`, o `setup(project=...)` por notebook). Los paneles y los filtros funcionan por proyecto. |
| **Dataset** | Un conjunto versionado de ejemplos (entradas + salidas de referencia) guardado en LangSmith para la evaluación offline. |
| **Experiment** | Una ejecución puntuada de tu aplicación sobre un dataset (`evaluate(target, data=..., evaluators=[...])`). Comparar dos experimentos es comparar dos versiones de la aplicación sobre los mismos ejemplos. |
| **Evaluator** | Una función que puntúa un run, con la firma `(inputs, outputs, reference_outputs) -> puntuación`: una heurística, una comprobación por código o un LLM-as-judge. Se usa offline en experimentos y online sobre trazas de producción. |
| **Feedback** | Una puntuación o un comentario asociado a un run (`client.create_feedback(run_id, key, score=...)`): el pulgar del usuario, la nota de un evaluador, una heurística. Es la señal de la evaluación online. |
| **OTel GenAI semantic conventions** | Nombres de atributo estándar de OpenTelemetry para telemetría de LLMs (`gen_ai.request.model`, `gen_ai.usage.input_tokens`, ...), para que las trazas puedan ir a cualquier backend. LangSmith puede recibir y exportar OpenTelemetry. |
| **p50 / p95 / p99** | Percentiles de latencia: el valor por debajo del cual cae el 50 / 95 / 99 % de las peticiones. Se reportan en lugar de la media, porque la cola es lo que notan los usuarios. |
| **SLO (Service-Level Objective)** | Objetivo para una métrica del servicio, p. ej. "p95 < 2 s, tasa de error < 1 %". Las violaciones disparan alertas. En serving, los SLOs se ponen sobre percentiles de TTFT y TPOT (p. ej. TTFT p95 < 1 s, TPOT p95 < 50 ms). (NB 28, 12) |
| **PII redaction** | Sustituir datos personales (emails, teléfonos, números de tarjeta, claves de API) por marcadores antes de que los prompts y las respuestas lleguen a logs o trazas. (NB 28) |
| **Head sampling** | Decidir al inicio de una traza si se conserva entera (en LangSmith, `LANGSMITH_TRACING_SAMPLING_RATE=0.1` conserva el 10 % de las trazas). El *tail sampling* decide al final, p. ej. para conservar todos los errores. |
| **Bootstrap confidence interval** (intervalo de confianza bootstrap) | Remuestrear con reemplazo las puntuaciones por ejemplo (p. ej. 2.000 veces), recalcular la media cada vez y tomar los cuantiles 2,5 % y 97,5 %: un intervalo del 95 % sin suponer ninguna distribución. Con 20 preguntas sale ancho, y eso es información. (`evaluation.bootstrap_ci`, NB 18, 23) |
| **Paired bootstrap** (bootstrap pareado) | El mismo remuestreo aplicado a las diferencias por ejemplo entre dos sistemas evaluados sobre los mismos ejemplos (preguntas, usuarios). Emparejar cancela la variación por dificultad de cada ejemplo; si el intervalo de la diferencia excluye el 0, la diferencia difícilmente es ruido. (`evaluation.paired_bootstrap_diff`, NB 18, 23) |

## Frameworks de evaluación y trazas

| Término | Significado |
|---|---|
| **Inspect AI** | El framework de evaluación de código abierto del UK AI Security Institute (MIT). Una evaluación es una *tarea* que se ejecuta desde la línea de comandos (`inspect eval`) contra la API de cualquier modelo, Ollama incluido, y cada ejecución deja un log que se puede recorrer con `inspect view`. Está pensado para evaluar sistemas (prompts, herramientas, agentes, sandboxes) más que checkpoints de modelos. (NB 29, `scripts/inspect_tasks/gsm8k_cot.py`) |
| **Task / solver / scorer** (tarea / solver / scorer, Inspect) | Las tres piezas de una evaluación de Inspect. La *tarea* une un dataset de `Sample`s con un solver y uno o varios scorers. El *solver* es lo que se le hace a cada muestra: un mensaje de sistema, una generación, una cadena de pensamiento, uso de herramientas, un bucle de agente en un sandbox. El *scorer* puntúa la salida (coincidencia exacta, una expresión regular, un modelo que corrige) y declara sus métricas (`accuracy()`, `stderr()`). En el NB 29, dos scorers sobre las mismas generaciones se separan 5 puntos (85,0 % frente a 80,0 %). |
| **Epochs** | Ejecutar cada muestra de una evaluación varias veces y reducir las puntuaciones (media, mayoría), porque con un modelo muestreado una ejecución es una tirada (`inspect eval --epochs 3`). En el NB 29, tres epochs a T = 0,7 dan 80,0, 82,5 y 81,2 %, y solo 2 de los 80 problemas cambian entre ellas. |
| **Evaluation log** (log de evaluación) | El registro de una ejecución de una evaluación: para cada muestra, la entrada, la referencia, los mensajes, la salida, la puntuación y la respuesta extraída de cada scorer, los tokens y los tiempos, además de los ajustes de la ejecución (modelo, temperatura, tokens máximos). Es lo que permite comparar ejecuciones meses después. En el NB 29, 1,9 MB de JSON para 80 muestras. |
| **OpenTelemetry (OTel)** | El estándar abierto (CNCF) para trazas, métricas y logs: un SDK en la aplicación, el protocolo OTLP (sobre HTTP o gRPC) y cualquier backend compatible. Como el protocolo es abierto, pasar de Phoenix a Langfuse, LangSmith o Datadog es un cambio de configuración. (NB 29) |
| **Span** | Un paso cronometrado dentro de una traza: una cadena, un prompt, una llamada al LLM, una recuperación, una llamada a una herramienta, con su hora de inicio y de fin, un estado, atributos y un span padre. Una traza es el árbol de spans de una petición. En el NB 29, cada petición de GSM8K es una traza de 5 spans, y el span del LLM es toda la latencia (p50 3.585 ms; todos los demás pasos por debajo de 1 ms). |
| **OpenInference** | El conjunto de nombres de atributo y tipos de span de OpenTelemetry que propone Arize para el trabajo con LLMs (`llm.model_name`, `llm.token_count.prompt`, `input.value`, `output.value`; tipos `LLM`, `CHAIN`, `RETRIEVER`, `TOOL`...), con instrumentadores para LangChain, LlamaIndex, el SDK de OpenAI y otros. Emparentado con las convenciones semánticas GenAI de OTel, que buscan lo mismo. (NB 29) |
| **Instrumentor / exporter** (instrumentador / exportador) | Un *instrumentador* se engancha a una librería y crea sus spans automáticamente, sin cambiar el código de la aplicación (`LangChainInstrumentor().instrument(...)`); un *exportador* envía los spans, normalmente por lotes, a un colector o un backend por OTLP. En el NB 29 la exportación por lotes añade 2,5 ms por petición, el 0,07 % de una llamada al LLM. |
| **Phoenix** | El servidor de trazas y evaluación de código abierto de Arize para aplicaciones con LLMs (Elastic License 2.0), construido sobre OpenTelemetry y OpenInference. Corre como un único proceso de Python con SQLite (`phoenix serve`), con una interfaz web y una API REST para spans y anotaciones; `arize-phoenix-otel` es su parte cliente. (NB 29) |
| **Annotation** (anotación, sobre un span) | Una etiqueta o una puntuación que se pega a un span a posteriori, desde código, un juez LLM o una persona, para que las trazas se conviertan en datos de evaluación que se pueden buscar ("enséñame las peticiones que fallaron"). En el NB 29, si cada petición acertó, calculado con código, se publica en Phoenix sobre su span raíz y se lee de vuelta: 80 % en 20 problemas. |

## Seguridad y guardrails

| Término | Significado |
|---|---|
| **Jailbreak** | Un prompt que consigue que un modelo alineado haga lo que su entrenamiento de seguridad le enseñó a rechazar. A diferencia de la inyección de prompts, que ataca a una *aplicación* a través de los datos que lee, un jailbreak ataca los valores del propio modelo, normalmente desde el turno del usuario. (NB 30) |
| **Competing objectives** (objetivos en competencia) | Uno de los dos modos de fallo del entrenamiento de seguridad que describen Wei et al. (2023): el modelo se entrenó para seguir instrucciones y también para rechazar lo dañino, y un prompt enfrenta las dos cosas. La inyección de prefijo y la supresión del rechazo se aprovechan de ello. (NB 30) |
| **Mismatched generalization** (generalización desajustada) | El otro modo de fallo de Wei et al. (2023): el entrenamiento de seguridad cubrió menos situaciones que el de capacidades, así que una petición envuelta en ficción o en un juego de rol, traducida o codificada queda fuera de lo que vio el entrenamiento de rechazo, mientras el modelo sigue sabiendo hacer la tarea. (NB 30) |
| **Prefix injection** (inyección de prefijo) | Un jailbreak que pide al modelo que empiece su respuesta con una frase afirmativa; una vez que los primeros tokens ceden, lo más probable es seguir por ahí. En el NB 30 tumba a `qwen2.5:3b` en el 64 % de los comportamientos de JailbreakBench, frente al 4 % con la petición directa. |
| **Refusal suppression** (supresión del rechazo) | Un jailbreak que prohíbe, como reglas de la respuesta, las disculpas, los avisos y las palabras de las que están hechos los rechazos. En el NB 30 llega a un 24 % de éxito. |
| **Over-refusal / exaggerated safety** (sobre-rechazo / seguridad exagerada) | Rechazar peticiones seguras que solo *suenan* peligrosas (matar un proceso, disparar una foto, la trama de una novela policiaca), un atajo aprendido en el entrenamiento de rechazo. Le cuesta usuarios al producto y les enseña a esquivar el sistema. En el NB 30, el 17 % de los prompts seguros de XSTest con `qwen2.5:3b` y el 5 % con `qwen2.5:7b`. |
| **Refusal rate** (tasa de rechazo) | La proporción de prompts que un modelo rechaza. Con prompts dañinos, cuanto más alta, más seguro; con prompts seguros es la tasa de sobre-rechazo, y cuanto más baja, mejor. Se suele puntuar con un juez por palabras clave o con un juez LLM, y los dos hay que validarlos con etiquetas humanas (NB 30: 89,7 % de acuerdo para el juez por palabras clave, 70,0 % para un juez LLM de 7B). |
| **Attack success rate, ASR** (tasa de éxito del ataque) | La proporción de peticiones dañinas que producen una respuesta dañina. Una respuesta que no rechaza no tiene por qué ser dañina, así que el ASR se puntúa con un juez de nocividad (el clasificador de HarmBench, el juez de JailbreakBench, la rúbrica de StrongREJECT, Llama Guard), no detectando rechazos. (NB 30) |
| **StrongREJECT** | Un benchmark de jailbreaks y una rúbrica de puntuación (Souly et al., 2024) que mide lo *útil* que es de verdad una respuesta obtenida con un jailbreak, tras demostrar que puntuar solo "¿ha rechazado?" exagera el éxito de los jailbreaks. |
| **Guard model** (modelo guardián) | Un clasificador aparte, delante del modelo (filtro de entrada) o detrás (filtro de salida), que etiqueta los prompts o las respuestas como seguros o inseguros. Es barato e independiente del modelo que protege, así que un mismo guardián cubre todos los modelos que tenga detrás; tiene sus propios falsos positivos y sus fallos. Llama Guard, ShieldGemma y Granite Guardian son abiertos; el endpoint de moderación de OpenAI, Azure AI Content Safety y Amazon Bedrock Guardrails son servicios gestionados. (NB 30) |
| **Llama Guard** | La familia de modelos guardián de Meta (Inan et al., 2023): un LLM ajustado para responder `safe` o `unsafe`, más una categoría de riesgo, sobre un prompt del usuario o una respuesta del asistente. Llama Guard 3 usa la taxonomía S1–S14 de MLCommons (delitos violentos, delitos no violentos, delitos sexuales, explotación infantil, difamación, asesoramiento especializado, privacidad, propiedad intelectual, armas de destrucción masiva, odio, autolesiones, contenido sexual, elecciones y abuso del intérprete de código). En el NB 30, `llama-guard3:1b` con Ollama marca el 95–100 % de las peticiones dañinas y el 8 % de los prompts seguros de XSTest, a 39–62 ms por prompt. |
| **Red-teaming** | Atacar a propósito tu propio sistema, a mano o con herramientas (PyRIT, garak, el modo red-team de promptfoo), para encontrar los prompts que lo rompen antes que los usuarios. Cada ataque que funciona pasa al conjunto de prueba. (NB 30) |
| **GCG (Greedy Coordinate Gradient)** | Un jailbreak automático (Zou et al., 2023) que optimiza un sufijo adversario token a token con los gradientes de un modelo abierto; los sufijos a menudo se transfieren a otros modelos. No se ejecuta en el curso. |
| **PAIR (Prompt Automatic Iterative Refinement)** | Un jailbreak automático de caja negra (Chao et al., 2023) en el que un LLM atacante reescribe un prompt en bucle, guiándose por las respuestas del objetivo y la nota de un juez, hasta que funciona, a menudo en unas veinte consultas. No se ejecuta en el curso. |
| **XSTest** | Una batería de pruebas de seguridad exagerada (Röttger et al., 2024): 250 prompts seguros pensados para activar los atajos de rechazo (homónimos, lenguaje figurado, contextos seguros, preguntas sobre la privacidad de personajes de ficción) y 200 prompts inseguros de contraste. Sus autores publicaron también respuestas de modelos etiquetadas por personas, que el NB 30 usa para validar su juez de rechazos (`Paul/XSTest`, `natolambert/xstest-v2-copy`). |
| **JailbreakBench** | Un benchmark abierto de jailbreaks (Chao et al., 2024): 100 comportamientos dañinos en diez categorías, cada uno con una cadena objetivo y un gemelo benigno sobre el mismo tema, más una clasificación pública y un juez estándar. El NB 30 usa los comportamientos, los objetivos y los gemelos (`JailbreakBench/JBB-Behaviors`). |

## MCP

| Término | Significado |
|---|---|
| **MCP (Model Context Protocol)** | Protocolo abierto que estandariza cómo las aplicaciones LLM obtienen herramientas, datos y prompts de programas externos, sobre JSON-RPC 2.0. (NB 26, `scripts/mcp_server.py`) |
| **MCP host / client / server** | El host es la aplicación que usa la persona (Claude Code, Claude Desktop, un IDE, tu agente); ejecuta un cliente por cada servidor; el servidor es el programa que expone las capacidades. |
| **Tool / resource / prompt (MCP)** | Las tres primitivas de un servidor: herramientas que llama el modelo, recursos de solo lectura que la aplicación carga en el contexto (URIs fijas o plantillas de URI como `docs://{name}`) y plantillas de prompt que elige el usuario. |
| **Tool annotations** | Pistas que el servidor asocia a una herramienta (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) para que el host pueda decidir, por ejemplo, pedir confirmación antes de una llamada destructiva. Son pistas, no garantías. |
| **FastMCP** | La API de alto nivel para servidores del SDK oficial de MCP para Python (`mcp.server.fastmcp.FastMCP` en 1.x): `@server.tool()`, `@server.resource(uri)` y `@server.prompt()` convierten funciones en primitivas, derivando el JSON Schema de las anotaciones de tipo y la descripción del docstring; `server.run()` sirve por stdio y `server.run(transport="streamable-http")` por HTTP. |
| **MCP adapters (`langchain-mcp-adapters`)** | Librería que convierte las herramientas de uno o varios servidores MCP en herramientas de LangChain: `MultiServerMCPClient({...}).get_tools()`, listas para `create_agent`. `tool_name_prefix` pone espacio de nombres a herramientas de servidores distintos. (NB 26) |
| **JSON-RPC request vs notification** | Una petición lleva `id` y siempre recibe respuesta (`result` o `error`); una notificación no lleva `id` y nunca la recibe (p. ej. `notifications/initialized`). |
| **Protocol error vs tool error (`isError`)** | Un `error` de JSON-RPC significa que la petición en sí estaba mal (método desconocido, parámetros incorrectos); un resultado con `isError: true` significa que la herramienta se ejecutó y falló, para que el modelo lo vea y reintente. |
| **stdio transport** | El host lanza el servidor como subproceso e intercambia un mensaje JSON por línea por stdin/stdout. stdout queda reservado para el protocolo: los logs van a stderr. |
| **Streamable HTTP transport** | El servidor escucha en un único endpoint HTTP (p. ej. `/mcp`); el cliente envía mensajes JSON-RPC por POST y el servidor responde con JSON o con un *event stream*, manteniendo una sesión con la cabecera `mcp-session-id`. Para servidores remotos o compartidos. |
| **Tool poisoning** | Ataque en el que un servidor MCP malicioso esconde instrucciones en la descripción de una herramienta (que lee el modelo, rara vez el usuario) o la cambia después de aprobarla. Mitigaciones: listas blancas, espacios de nombres, revisar descripciones, confirmación para herramientas arriesgadas. |
| **Sampling (MCP)** | Una petición de servidor a cliente (`sampling/createMessage`) en la que el servidor pide una respuesta al modelo del host, así que no necesita modelo ni clave de API propios. El host puede enseñar la petición, cambiar de modelo, limitar los tokens o negarse. (NB 26) |
| **Elicitation (MCP)** | Una petición de servidor a cliente (`elicitation/create`) que pide al *usuario*, no al modelo, datos estructurados o una confirmación descritos con un esquema JSON; la respuesta es accept, decline o cancel. No sirve para contraseñas ni secretos. (NB 26) |
| **Roots (MCP)** | Las carpetas o repositorios en los que un cliente le dice a un servidor que puede trabajar (`roots/list`). Son orientativas: un servidor cooperativo se queda dentro, uno malicioso puede ignorarlas. (NB 26) |
| **Resource server / authorization server** (servidor de recursos / de autorización) | Papeles de OAuth. El servidor de autorización emite los tokens de acceso; el servidor de recursos (un servidor MCP remoto) acepta las peticiones que traen un token válido para él y, si no, responde `401` con `WWW-Authenticate`. (NB 26) |
| **Protected-resource metadata, RFC 9728** (metadatos del recurso protegido) | Un documento JSON que publica un servidor de recursos en `/.well-known/oauth-protected-resource`, con los servidores de autorización en los que confía y los scopes que admite; la cabecera `WWW-Authenticate` de un 401 apunta a él. (NB 26) |
| **Bearer token** | Un token de acceso que se envía como `Authorization: Bearer <token>`: quien lo tiene está autorizado, así que se hace de vida corta y con scope limitado, se mantiene fuera de los logs y de la línea de comandos, y se valida (firma, caducidad, scope, audiencia) en cada petición. (NB 26, `mcp_server.py --require-token`) |
| **Token passthrough** | El antipatrón, prohibido por la especificación de MCP, de un servidor que acepta tokens emitidos para otro servicio o reenvía el token del cliente a las APIs que llama por detrás. Convierte al servidor en un *confused deputy*; validar la audiencia (resource indicators, RFC 8707) lo evita. (NB 26) |
