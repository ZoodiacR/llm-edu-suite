# Glossary

[← Back to the index](README.md)

Short definitions of the terms used across the suite. In brackets, the module, library or notebook (NB) where each one appears. The last column gives the term used in the Spanish docs, where it differs from the English one (many terms are kept in English in Spanish too, because that is how they appear in papers, libraries and job postings).

## Tokenization and architecture

| Term | Meaning | Spanish docs |
|---|---|---|
| **Token** | The smallest unit the model processes: a word piece, a frequent word or a single byte. | token |
| **BPE (Byte-Pair Encoding)** | Builds the vocabulary by repeatedly merging the most frequent pair of symbols. The *byte-level* variant starts from the 256 bytes, so it never produces `<UNK>`. (`tokenizer.py`, NB 01) | |
| **Fertility** | Average number of tokens per word. Higher = the tokenizer splits text more (typical for under-represented languages). | |
| **Compression ratio** | Bytes of text per token. Higher = shorter sequences = cheaper inference. | relación de compresión |
| **Embedding** | A learned vector that represents a token (or a document, or an item in a recommender). | |
| **Decoder-only / causal LM** | A transformer that predicts the next token and can only look backwards (causal mask). The architecture of GPT, Llama, Qwen, DeepSeek, SmolLM2. (`model.py`) | |
| **Self-attention** | Each position computes a weighted average of the others: `softmax(QKᵀ/√d)·V`. Cost O(T²) in the sequence length T. | autoatención |
| **MHA / GQA / MQA** | *Multi-Head*, *Grouped-Query* and *Multi-Query Attention*. GQA shares each K/V head across several Q heads to shrink the KV-cache. (`layers.py`, NB 02) | |
| **MLA (Multi-head Latent Attention)** | DeepSeek-V2/V3 technique: compresses K and V into a small latent vector, which is the only thing kept in the cache. | |
| **RoPE (Rotary Position Embedding)** | Encodes position by rotating pairs of dimensions of Q and K, so the QKᵀ product depends only on the relative distance. Two conventions choose the pairs: interleaved (2i, 2i+1), used by Meta's original Llama and by this course, and *rotate_half* (i, i+d/2), used by Hugging Face; they are equivalent once the rows of W_q and W_k are permuted. | |
| **Checkpoint / safetensors** | A published model is code (the architecture) + `config.json` (hyperparameters) + weights. `safetensors` is the standard weight format: a name → tensor dictionary that loads without running code and can be memory-mapped. | checkpoint / safetensors |
| **RMSNorm** | Normalization that only divides by the root mean square (no mean subtraction). Cheaper than LayerNorm; standard in Llama. | |
| **Pre-norm / sandwich norm / QK-norm** | Where the normalizations go: before each sub-block, before and after it, or on Q and K to stabilize training. | |
| **SwiGLU** | Gated FFN: `W_down(SiLU(W_gate·x) ⊙ W_up·x)`. Standard in modern LLMs. | |
| **MoE (Mixture of Experts)** | Replaces the FFN with N experts and a *router* that activates only k of them per token: many total parameters, few active ones. (NB 04) | mezcla de expertos |
| **Aux-loss vs aux-free balancing** | Two ways to stop the router from always picking the same experts: an auxiliary loss, or a per-expert bias adjusted without gradients (DeepSeek-V3). | balanceo con / sin pérdida auxiliar |
| **Shared expert** | An expert that always processes every token, on top of the routed ones. | experto compartido |
| **Sliding-window / Longformer / block-sparse / linear attention** | Efficient attention variants for long contexts: local window, window + global tokens, content-selected blocks, and O(T) linear attention. (NB 03) | |
| **Attention sink** | A position (often the first token or the end-of-sequence token) where a layer parks attention probability when it has nothing specific to read. It must be kept when trimming the KV-cache, and in attention maps it hides the real alignment. (NB 03, NB 17) | attention sink |
| **Encoder-only** | A transformer with bidirectional attention (no causal mask): every token sees every other. It does not generate; it gives each position a representation that depends on the whole input. BERT, RoBERTa, DeBERTa, ModernBERT. Used for classification, entities, embeddings and rerankers. In the course, `ModelConfig(causal=False)`. (NB 17) | encoder-only |
| **Encoder-decoder** | A transformer with both halves of the original: a bidirectional encoder reads the input once and a causal decoder writes the output while reading the encoder states through *cross-attention*. T5, BART, Flan-T5, Whisper. Strong for translation and speech. (NB 17) | encoder-decoder |
| **MLM (masked language modeling)** | BERT's pre-training objective: 15 % of the positions are hidden (80 % `[MASK]`, 10 % a random token, 10 % unchanged) and the model recovers them from both sides. Only the hidden positions are graded; ELECTRA uses all of them with *replaced token detection*. (NB 17) | modelado de lenguaje enmascarado |
| **Cross-attention** | Attention whose queries come from one sequence (the output the decoder is writing) and whose keys and values come from another (the encoder states). In T5, each decoder block is self-attention → cross-attention → FFN. (NB 17) | cross-attention |
| **[CLS] / pooling** | Two ways to summarize a sentence in one vector from an encoder: the state of the special first token `[CLS]`, or the mean of all token states (*mean pooling*, ignoring padding through the attention mask). (NB 17) | [CLS] / pooling |
| **Classification head** | A linear layer on the sentence vector that gives a distribution over a fixed label set, `softmax(W·h + b)`. `AutoModelForSequenceClassification` adds it randomly initialised and it is fine-tuned together with the encoder. (NB 17) | cabeza de clasificación |
| **ModernBERT** | A 2024 encoder (Warner et al.) that applies what decoders learned to BERT: RoPE, GeGLU, pre-norm, global layers alternating with 128-token windows, *unpadding* and an 8,192-token context. The base version (150M) reaches 93.0 % on Banking77 when fine-tuned. (NB 17) | ModernBERT |
| **Linear probe** | A linear classifier (for example logistic regression) trained on frozen representations. It measures how much task-relevant information they already hold; in NB 17, frozen ModernBERT gives 89.2 % and `nomic-embed-text` 93.3 % on Banking77. | linear probe |

## Pre-training data

| Term | Meaning | Spanish docs |
|---|---|---|
| **FineWeb / FineWeb-Edu** | Hugging Face's open corpora (Penedo et al., 2024) built from Common Crawl, with every pipeline step (filters, deduplication) validated by ablations on small models. FineWeb-Edu is the subset a classifier scores 3 or more for educational value. ODC-By license. NB 18 uses samples of 12,000 and 1,000 documents, downloaded into `data/cache/` and not redistributed. | FineWeb / FineWeb-Edu |
| **Deduplication** | Removing repeated documents from the corpus. **Exact** dedup compares a hash (e.g. SHA-1) of the normalized text: linear and cheap, but one changed character defeats it. **Near-duplicate** dedup uses MinHash + LSH. It cuts compute, memorization and evaluation leaks. (NB 18) | deduplicación |
| **Near-duplicate** | A document that is almost the same as another: the same page in another template, or with a few words changed. Exact hashing misses it; it is detected by shingle overlap (Jaccard similarity). (NB 18) | casi-duplicado |
| **Shingle** | Each of the overlapping n-grams (of words or characters) a document is broken into so it can be compared with others as a set. With word 5-grams, editing one word breaks up to five shingles. (NB 18) | shingle |
| **Jaccard similarity** | Overlap between two sets, `J(A, B) = \|A ∩ B\| / \|A ∪ B\|`, between 0 and 1. On shingle sets it measures how much text two documents share. (NB 18) | similitud de Jaccard |
| **MinHash** | An estimator of Jaccard similarity (Broder, 1997): apply a random hash function to every shingle and keep the minimum; the probability that two documents share the minimum is exactly their Jaccard. With k hash functions, the signature of k minima estimates J with standard error `√(J(1−J)/k)`. In NB 18, k = 128 affine functions modulo a Mersenne prime. | MinHash |
| **LSH (locality-sensitive hashing)** | A way to find candidate pairs without comparing everything with everything: the MinHash signature is split into b bands of r rows and two documents are candidates if they match on any whole band. The probability, `1 − (1 − J^r)^b`, is an S-curve with a threshold near `(1/b)^(1/r)`; with 16 × 8, about 0.71. (NB 18) | LSH |
| **Quality filter** | A step that drops documents not worth training on. **Heuristic** filters (the Gopher and C4 rules: length, symbols, bullets, stop words, lines without terminal punctuation) remove what is not prose; **model-based** filters (the FineWeb-Edu classifier, a 110M BERT; DCLM's fastText) score what the text is worth, with the bias of whoever labelled their data. (NB 18) | filtro de calidad (heurístico / basado en modelo) |
| **Decontamination** | Removing (or reporting) training documents that contain text from evaluation benchmarks, usually by looking for shared long n-grams (8 to 13 tokens). It catches verbatim copies, not paraphrases. In NB 18 it finds all 50 planted leaks plus 29 natural overlaps from syndicated news. | descontaminación |
| **Model collapse** | The progressive loss of diversity when a model is trained repeatedly on model-generated text: the tails of the distribution go first (Shumailov et al., 2024). That is why synthetic data is deduplicated, filtered and measured for diversity (e.g. distinct bigrams: 0.60 for `qwen2.5:3b` text against 0.72 for human text, NB 18). | model collapse |

## Training and post-training

| Term | Meaning | Spanish docs |
|---|---|---|
| **Pre-training** | Training from scratch on next-token prediction over a large corpus. What happens to the data before that is under [Pre-training data](#pre-training-data). (NB 05) | preentrenamiento |
| **Perplexity** | `exp(mean loss)`. Intuition: how many tokens the model is "hesitating" between. Lower is better. | perplejidad |
| **Warmup / cosine / WSD** | Learning-rate schedules: initial ramp-up; cosine decay; or *Warmup-Stable-Decay* (constant, then a final drop). | calentamiento |
| **AdamW / weight decay** | The standard optimizer. Weight decay is not applied to norms or biases (parameter groups). | |
| **Gradient accumulation / clipping / AMP** | Simulate large batches, cap the gradient norm, and use mixed precision (bf16/fp16). | acumulación / recorte de gradiente, precisión mixta |
| **Gradient checkpointing / activation checkpointing** | Recomputing activations during the backward pass instead of storing them (in PyTorch, `torch.utils.checkpoint.checkpoint` around each block): less memory, about 30 % more compute. On by default in `scripts/finetune.py`. In NB 19 it cuts peak memory by 57 % in fp32 for ~22 % more time per step. | |
| **Mixed precision / bf16** | Compute in bf16 or fp16 on the tensor cores and keep fp32 master weights. bf16 has fp32's exponent range and needs no *loss scaling*; fp16 does. In PyTorch, `torch.autocast("cuda", dtype=torch.bfloat16)`. (NB 19: a step 2.2× faster than fp32) | precisión mixta |
| **MFU (model FLOPs utilization)** | The share of the GPU's peak FLOP/s that is useful model work: tokens/s × 6N FLOPs per token (plus attention) divided by the peak. Well-tuned large training runs reach 40–60 %. (NB 19: 32 %) | |
| **DDP (DistributedDataParallel)** | PyTorch's data parallelism: one process per GPU, each with the whole model and its shard of the batch; an all-reduce averages the gradients before the optimizer step, so it is equivalent to training with the global batch. (NB 19) | |
| **All-reduce** | A collective operation that sums (or averages) a tensor across all processes and leaves the result on all of them. With a ring, each process sends about 2(k−1)/k · P bytes for a P-byte tensor, almost independent of the number of processes k. NCCL on GPU, gloo on CPU. | |
| **ZeRO (Zero Redundancy Optimizer)** | DeepSpeed's technique (Rajbhandari et al., 2020) that shards across the data-parallel GPUs, instead of replicating them, the optimizer states (stage 1), also the gradients (stage 2) and also the weights (stage 3). With 8 GPUs, a 7B model goes from 112 GB per GPU to 14 GB at stage 3. (NB 19) | |
| **FSDP (Fully Sharded Data Parallel)** | PyTorch's version of ZeRO-3 (`fully_shard` in FSDP2): each GPU stores a shard of the weights, gradients and states, and all-gathers each layer's weights right before using them. | |
| **Tensor parallelism** | Splitting each matmul across GPUs (by columns and by rows, as in Megatron-LM), with an all-reduce inside every layer. It needs fast links, so it is used within one node (NVLink). | paralelismo de tensor |
| **Pipeline parallelism** | Splitting the layers into stages, one per group of GPUs, and passing micro-batches from one to the next. It pays an idle "bubble" while the pipeline fills and drains (GPipe, 1F1B). | paralelismo de pipeline |
| **SFT (Supervised Fine-Tuning)** | Tuning the model on instruction→response pairs, usually rendered with the model's **chat template**. (NB 07) | ajuste fino supervisado |
| **Completion-only loss / loss masking** | Computing the SFT loss only on the response tokens: the prompt tokens get label `-100`, so the cross-entropy ignores them. TRL does it automatically for *prompt-completion* datasets. (NB 07) | enmascarado de pérdida |
| **SFTTrainer** | TRL's trainer for SFT: takes a conversational or prompt-completion dataset, applies the chat template, masks the prompt, and accepts a `peft_config` to train LoRA adapters. Configured with `SFTConfig`. (`scripts/finetune.py`, NB 07) | |
| **LoRA** | Freezes W and learns a low-rank correction `W + (α/r)·B·A`. With B=0 at init, the model starts identical to the base; after training it can be *merged* (`merge_and_unload` in `peft`) at no inference cost. (NB 07) | |
| **LoRA `modules_to_save`** | `peft` option that trains (and saves) full copies of chosen modules next to the adapters, typically the embedding and `lm_head`. Needed when fine-tuning introduces tokens the base model never learned, such as new chat-role tokens. (NB 07) | |
| **QLoRA** | LoRA on a base model whose frozen weights are stored in 4 bits (NF4); the adapters stay in bf16 and every matmul dequantizes the weight first. It saves weight memory (a 7B model goes from ~14 GB to ~3.6 GB), not activation memory, and each step is a little slower. In `transformers`, `BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4", ...)` + `prepare_model_for_kbit_training`. (NB 07) | QLoRA |
| **Double quantization** | Quantizing the per-block scales too (to 8 bits): the overhead drops from 0.5 to about 0.127 bits per parameter. One of QLoRA's three ideas (`bnb_4bit_use_double_quant=True`). (NB 07) | doble cuantización |
| **Paged optimizer** | Optimizer state lives in CUDA unified memory and is paged to CPU RAM when memory spikes, instead of failing with out-of-memory (`optim="paged_adamw_8bit"`). (NB 07) | optimizador paginado |
| **Distillation** | A *student* model learns to imitate a *teacher's* distribution (KL between logits). (NB 07) | destilación |
| **Model merging** | Combining several fine-tunes of the same base into one set of weights with arithmetic alone: no data, no training. With adapters, `peft`'s `add_weighted_adapter`; with full models, `mergekit`. It puts the behaviours side by side but does not combine them into a new skill; when all the data is available, multi-task training usually does better. (NB 07) | fusión de modelos |
| **Task vector** | What a fine-tune changed: `τ = θ_fine-tuned − θ_base` (Ilharco et al., 2023). With LoRA, `(α/r)·B·A` for each adapted matrix. Two task vectors for unrelated tasks are nearly orthogonal (in NB 07, mean cosine +0.012). (NB 07) | |
| **Task arithmetic** | Merging by adding (or subtracting) task vectors: `θ = θ_base + Σ λ_t·τ_t`. Adding gives a model that does both tasks; subtracting removes a behaviour. For LoRA, `combination_type="cat"` or `"svd"` in `peft` computes it exactly. (NB 07) | |
| **Model soup** | The average of several fine-tunes of the same task with different hyperparameters (Wortsman et al., 2022): often better and more robust than the best single run, at no extra inference cost. (NB 07) | |
| **Linear mode connectivity** | Two fine-tunes of the same pretrained model are joined by a straight path in weight space along which the loss stays low (Frankle et al., 2020). It is why averaging or adding their weights works, and why it fails for networks trained from different random initializations. (NB 07) | |
| **TIES-Merging** | A merging method for overlapping task vectors (Yadav et al., 2023): *trim* each one to its largest values, *elect* a sign per coordinate, and average only the values that agree with it. Useful when many fine-tunes interfere; with nearly orthogonal adapters (NB 07) it only threw signal away. | |
| **DARE (Drop And REscale)** | Randomly drops a fraction `p` of a task vector's coordinates and rescales the rest by `1/(1−p)` (Yu et al., 2024). Fine-tuning updates are so redundant that 90 % or more can go. Usually combined with TIES' sign election (`dare_ties`). (NB 07) | |
| **SLERP** | Spherical linear interpolation: blends two models along the sphere instead of a straight line, which keeps the norm of the weights. A popular `mergekit` method; only for two models at a time. (NB 07) | |
| **mergekit** | The standard toolkit for merging full models (Goddard et al., 2024): linear, SLERP, task arithmetic, TIES, DARE and more, configured in YAML, on CPU or GPU. Behind many of the merged open models on public leaderboards. (NB 07) | |
| **RLHF / preference tuning** | Aligning the model with human preferences: chosen vs rejected response. (NB 08) | alineamiento con preferencias |
| **DPO (Direct Preference Optimization)** | Optimizes preferences directly, with no reward model: `−log σ(β·[(log π−log π_ref)(y_w) − (log π−log π_ref)(y_l)])`. Equals ln 2 at init. | |
| **DPOTrainer** | TRL's trainer for DPO and its variants (`loss_type`). With a `peft_config`, the reference model is the same network with the adapter switched off, so no second copy is kept in memory. Configured with `DPOConfig` (`beta`, `loss_type`, `loss_weights`). (`scripts/finetune.py`, NB 08) | |
| **Likelihood displacement / DPO + NLL (RPO)** | DPO can widen the margin by pushing down the probability of *both* the chosen and the rejected answer. Adding the NLL (SFT loss) of the chosen answer counters it: in TRL, `loss_type=["sigmoid", "sft"]`. | |
| **GRPO (Group Relative Policy Optimization)** | RL from DeepSeekMath/R1: samples a group of responses per prompt and uses the reward normalized within the group as the advantage (no *critic*). A group where every sample gets the same reward gives no gradient. | |
| **GRPOTrainer** | TRL's trainer for GRPO: takes a prompt dataset and one or more Python **reward functions** `(completions, **columns) -> list[float]`, samples `num_generations` completions per prompt and optimizes the policy with a KL penalty (`beta`). Configured with `GRPOConfig`. (`scripts/finetune.py`, NB 08) | |
| **Verifiable reward** | A reward a program can compute (is the answer correct?), with no human or model judge. A *dense* reward gives partial credit, so groups are less likely to tie. | recompensa verificable |
| **KL penalty** | A term that keeps the policy from drifting too far from the reference model. | penalización KL |

## Reasoning and test-time compute

| Term | Meaning | Spanish docs |
|---|---|---|
| **Chain of thought (CoT)** | Having the model write its intermediate steps before the answer, with worked examples in the prompt (few-shot, Wei et al., 2022) or just "think step by step" (zero-shot). A transformer does a fixed amount of work per token, so the written steps are what give it serial computation. In NB 20 it takes `qwen2.5:3b` from 12.5 % to 85.0 % on GSM8K. | cadena de pensamiento |
| **Test-time compute** | Compute spent at inference on a single problem: longer reasoning, several samples, a verifier, revisions. Snell et al. (2024) treat it as a scaling axis of its own, next to parameters and data. It is paid in output tokens, the slow and expensive ones. (NB 20) | cómputo en inferencia |
| **Self-consistency** | Sampling several chains of thought at temperature > 0 and returning the most frequent final answer (Wang et al., 2022): correct paths tend to agree, wrong ones scatter. It needs answers that can be compared exactly. (NB 20: 90.0 % with 5 samples against 85.0 % greedy) | |
| **maj@k** | Accuracy of the majority vote among k samples, that is, of self-consistency with k samples. It rises with k and saturates. (NB 20) | |
| **pass@k** | The probability that at least one of k samples is correct: the ceiling a perfect verifier would reach with those samples. The gap between pass@k and maj@k is the most a verifier can add on top of voting. Unbiased estimate from n samples with c correct: `1 − C(n−c, k) / C(n, k)` (Chen et al., 2021). (NB 20: 91.2 % from k = 3) | |
| **Best-of-N** | Generating N candidates and returning the one a verifier or reward model scores highest. It only helps if the verifier discriminates better than a vote; with a weak one it picks fluent wrong answers. (NB 20: 85.0 % with a 7B judge against 90.0 % for the vote) | |
| **Verifier / reward model (ORM, PRM)** | A model or program that scores a candidate answer. An *outcome* reward model (ORM) scores the final answer (Cobbe et al., 2021); a *process* reward model (PRM) scores every step (Lightman et al., 2023). Programmatic verifiers (tests, a calculator, a solver, a schema) are the most reliable. (NB 08, NB 20) | verificador / modelo de recompensa |
| **Reasoning model** | A model trained to think at length before answering, usually with RL on verifiable rewards (o1, DeepSeek-R1) or by distillation from another model's reasoning traces (R1-Distill). The thinking is emitted as tokens, often inside `<think>...</think>`, and billed as output. (NB 20: R1-Distill 1.5B, 63.7 % with 870 tokens per problem) | modelo de razonamiento |
| **Overthinking** | Reasoning that is too long for the problem: loops, second-guessing, or running out of token budget before answering. In NB 20, 16 of R1-Distill 1.5B's 80 answers hit the 2,048-token limit. | |
| **Bradley-Terry** | A model for pairwise comparisons: i beats j with probability `σ(β_i − β_j)`, with the β fitted by maximum likelihood (Bradley and Terry, 1952). It is behind RLHF reward models, DPO and Chatbot Arena's leaderboard; Elo is an online approximation. (NB 08, NB 20) | |
| **Position bias** | A pairwise judge (human or LLM) preferring the first or the second answer regardless of content (Zheng et al., 2023). It is measured and controlled by judging every pair in both orders and keeping only consistent verdicts. In NB 20, the 7B judge kept its verdict on only 43 % of 30 pairs when the order was swapped. | sesgo de posición |

## Inference and systems

| Term | Meaning | Spanish docs |
|---|---|---|
| **KV-cache** | Storing K and V of already-processed tokens so they are not recomputed at every generation step. Its size is often the memory bottleneck. (NB 02, 06) | |
| **Prefill / decode** | The phase that processes the prompt (parallel) and the phase that generates token by token (sequential, memory-bound). | |
| **TTFT (time to first token)** | From sending a request to receiving the first token: time in the queue + prefill + network. It grows with the prompt length and with the queue. (NB 06, 23: 101 → 645 ms from 338 to 2,322 prompt tokens) | tiempo hasta el primer token |
| **TPOT / inter-token latency** | *Time per output token*: the gap between tokens during decode. 1 / TPOT is the reading speed of one user; end-to-end latency ≈ TTFT + TPOT × (output tokens − 1). Batching raises it. (NB 23: 12.5 ms with one sequence, 23 ms with four per step) | tiempo por token de salida / latencia entre tokens |
| **Throughput / goodput** | Throughput: total output tokens per second across all users, what the hardware bill depends on. Goodput: the requests per second that meet the latency SLO, the capacity that actually counts (DistServe). | throughput / goodput |
| **Greedy / temperature / top-k / top-p** | Sampling strategies: the most likely token; flatten or sharpen the distribution; keep the k most likely; or keep the nucleus of cumulative probability p. `model.next_token_distribution` shows the resulting distribution. | muestreo |
| **Speculative decoding** | A small model (*draft*) proposes several tokens and the large one verifies them in a single pass. With the right acceptance rule, the output distribution is **identical** to the large model's. (`inference.py`, NB 06) | decodificación especulativa |
| **Continuous batching** | Batching scheduled at every decode step: sequences join and leave the batch as they arrive and finish, instead of waiting for the longest one (static batching). Introduced by Orca (Yu et al., 2022); standard in vLLM, SGLang and TGI. | batching continuo |
| **PagedAttention** | vLLM's way of storing the KV-cache in fixed-size blocks with a block table, like virtual-memory pages: almost no fragmentation, blocks shared between sequences, many more concurrent sequences per GPU (Kwon et al., 2023). | |
| **Slot** | In llama.cpp and Ollama, one sequence of the batch the server runs in parallel, with its own share of the KV-cache. Their number is fixed (`OLLAMA_NUM_PARALLEL`); requests beyond it wait in a queue. (NB 23: one slot vs four) | slot |
| **Prefix caching / prompt caching** | Keeping the KV-cache of a prompt prefix shared by many requests (system prompt, tools, documents) and reusing it instead of recomputing the prefill: automatic prefix caching in vLLM, RadixAttention in SGLang, a slot's cache in llama.cpp; providers sell it as *prompt caching*, with cheaper cached input tokens. It matches token by token from the start, so shared content goes first. (NB 23: 99.1 % of the prompt from the cache, TTFT 654 → 39 ms) | caché de prefijos / caché de prompts |
| **Little's law** | L = λW: requests in the system = arrival rate × time in the system, for any stable queue (Little, 1961). It turns capacity planning into arithmetic. (NB 23: 1.33 req/s × 3.00 s = 4.0 in flight) | ley de Little |
| **Quantization (INT8 / INT4 / NF4)** | Storing weights with fewer bits. *absmax* scales by the maximum absolute value; per-block scaling reduces the error; NF4 uses levels that are optimal for normally distributed weights. (NB 09) | cuantización |
| **optimum-quanto** | Hugging Face library that quantizes a PyTorch / `transformers` model in place: `quantize(model, weights=qint8 / qint4 / qfloat8)` swaps the linear layers for quantized ones and `freeze(model)` stores the quantized weights. Works on CPU and GPU. (NB 09) | |
| **NF4 (NormalFloat4)** | A 4-bit format with 16 levels placed at the quantiles of a normal distribution, with one absmax scale per block of 64 weights. Since pretrained weights are roughly normal, it loses less precision than int4 with evenly spaced levels. It is QLoRA's format (`bitsandbytes`). (NB 07, 09) | NF4 |
| **GGUF / Q4_K_M** | The file format and block-wise 4-bit quantization scheme that llama.cpp and Ollama use. `qwen2.5:3b` in Ollama is a Q4_K_M GGUF of about 1.9 GB. | |
| **k-quants** | llama.cpp's family of GGUF quantization types (Q2_K to Q6_K): super-blocks of 256 weights split into sub-blocks with quantized scales, with some sensitive tensors kept at higher precision (the `_S` / `_M` / `_L` suffix). Q8_0 is plain 8-bit blocks of 32. (NB 23: `qwen2.5:1.5b-instruct` in Q4_K_M takes 1.17 GB of GPU memory and decodes at 130 tok/s, against 3.28 GB and 64 tok/s in FP16) | |
| **Gateway (LLM gateway)** | A service between the applications and the models that gives them one API (usually OpenAI-compatible) and handles routing, retries, fallbacks, timeouts, rate limits, budgets, caching and logs in one place. LiteLLM, Portkey, OpenRouter, cloud AI gateways. (NB 23) | gateway |
| **Fallback / circuit breaker** | A fallback sends the request to the next model in a chain when one fails or times out. A circuit breaker stops sending traffic to a failing backend for a while, so it is not hammered while it recovers. Both need logging, or they hide a dead primary. (NB 23) | fallback / circuit breaker |
| **Cascade / model router** | Two ways of routing for cost. A cascade (FrugalGPT) asks the cheap model first and escalates to the expensive one only when an uncertainty signal fires; a router (RouteLLM) predicts before any call which model a request needs. Not to be confused with a LangGraph router node, which picks a specialist, not a model size. (NB 23: a 3B → 7B cascade, 85.0 % at 88 % of always-7B's GPU time) | cascada / router de modelos |
| **Ollama** | A local server for open models: `ollama pull` downloads a model, and the server (port 11434) offers a native API and an OpenAI-compatible one (`/v1`). The course's default provider for notebooks 10–16 (`qwen2.5:3b`, `nomic-embed-text`), used through `ChatOllama` / `OllamaEmbeddings` from `langchain-ollama`. | |
| **Arithmetic intensity / roofline** | FLOPs per byte moved from memory. The roofline model bounds performance by the minimum of the peak FLOP/s and intensity × bandwidth: large matmuls are compute-bound; element-wise operations, softmax and small-batch decoding are memory-bound. (NB 06, 19) | intensidad aritmética |
| **FlashAttention** | An exact, *IO-aware* attention kernel (Dao et al., 2022): it computes in tiles in the chip's SRAM with an online softmax and never writes the T × T matrix to HBM, so its memory is linear in T. FlashAttention-2 is not shipped in the Windows PyTorch wheels; there SDPA uses the memory-efficient or cuDNN kernels, built on the same idea. (NB 19) | |
| **Kernel fusion / `torch.compile`** | Merging several operations into one GPU kernel that reads and writes memory only once. `torch.compile` captures the model's graph, and its default backend, `inductor`, generates Triton kernels (unavailable on Windows). (NB 19) | fusión de kernels |
| **CUDA graph** | Recording a sequence of kernels once and replaying it with a single launch, removing the CPU cost of launching each kernel; it needs static shapes. `torch.compile(backend="cudagraphs")`; inference servers use it for decoding. (NB 19: 4.1× on a small model's forward pass) | |

## Embeddings and rerankers

| Term | Meaning | Spanish docs |
|---|---|---|
| **Bi-encoder** | A retrieval model that encodes the query and the document *separately* into one vector each (an encoder plus pooling: the mean of the token vectors or the `[CLS]` vector) and scores them by cosine similarity. Document vectors are computed once, offline, so search is one forward pass for the query plus a vector search. What "embedding model" means in retrieval: all-MiniLM, BGE, E5, nomic-embed. (NB 21) | |
| **Cross-encoder** | A model that reads the query and the document *together* in one transformer and outputs a relevance score, so every query token attends to every document token. More accurate than a bi-encoder, but it needs one forward pass per candidate, so it is only used to rerank a short list. (NB 21: ms-marco-MiniLM-L6-v2, bge-reranker-base) | |
| **Late interaction (ColBERT)** | A middle point between bi-encoder and cross-encoder: one vector is kept per token, and the score is the sum, over query tokens, of the best-matching document token (MaxSim) (Khattab and Zaharia, 2020). ColPali applies it to page images. | interacción tardía |
| **Retrieve-then-rerank** | The two-stage retrieval funnel: a cheap first stage (BM25, embeddings or both) returns 50–100 candidates and a cross-encoder reorders them. The same idea as the recommendation funnel. A reranker can only promote what the first stage found, so recall@100 of the first stage is its ceiling. (NB 12, NB 21) | recuperar y reordenar |
| **Contrastive learning / InfoNCE** | Training embeddings so that a query lands near its relevant documents and far from the rest. The InfoNCE loss (van den Oord et al., 2018) is a cross-entropy over the batch in which the "class" of each query is its own document, with similarities divided by a **temperature** τ (often 0.01–0.05). `sentence-transformers` calls it `MultipleNegativesRankingLoss` and writes it as `scale = 1/τ = 20`. (NB 21: by hand and the library give the same 0.18594) | aprendizaje contrastivo |
| **In-batch negatives** | In a batch of B (query, positive) pairs, the other B − 1 documents serve as negatives for each query, at no extra cost. Bigger batches make the task harder and the embeddings better. `BatchSamplers.NO_DUPLICATES` keeps the same text from appearing twice in a batch, where it would act as a false negative. (NB 21) | negativos del batch |
| **Hard negatives** | Negatives that a retriever (BM25 or an earlier model) ranks high but that are not relevant: the cases that actually confuse the model, and the main ingredient of DPR and of modern recipes. Mined negatives can be unlabelled positives (false negatives); filtering them with a reranker score is the usual fix. (NB 21: one BM25 hard negative per pair took fine-tuned MiniLM from 0.723 to 0.762 nDCG@10) | negativos difíciles |
| **Task prefix (instruction)** | A fixed string that asymmetric embedding models expect before queries and documents, such as `search_query:` / `search_document:` (nomic) or `query:` / `passage:` (E5). Forgetting it is a silent bug: nothing fails, quality just drops. (NB 21: +0.006 for nomic on SciFact, within the noise) | prefijo de tarea |
| **Matryoshka embeddings (MRL)** | Embeddings trained with the contrastive loss summed over several prefix lengths (e.g. 384, 256, 128, 64), so the first m dimensions are a good embedding on their own and vectors can be truncated after the fact (Kusupati et al., 2022). OpenAI's `text-embedding-3` (`dimensions=`) and nomic-embed v1.5 are trained this way. (NB 21: 0.646 at 64 dimensions against 0.589 without the loss) | |
| **Embedding quantization (int8 / binary)** | Storing each dimension of a vector in one byte (int8, 4× smaller, calibrated on the corpus) or one sign bit (binary, 32× smaller, compared with the Hamming distance). Not the same as quantizing model weights. `sentence_transformers.quantization.quantize_embeddings`. (NB 21: 48 bytes per document instead of 1,536) | cuantización de embeddings |
| **Rescoring** | Retrieving candidates with cheap codes (binary) and reordering the top ones with more precise vectors (float or int8), which recovers most of the quality lost. It reorders but does not change recall. (NB 21: binary 0.709 → 0.760 with int8 rescoring, against 0.762 for float32) | |
| **BEIR** | A collection of heterogeneous retrieval datasets for zero-shot evaluation (Thakur et al., 2021), with nDCG@10 as its headline metric. It showed that BM25 is a hard baseline out of domain. SciFact and NFCorpus, used in NB 21, are two of its datasets. | |
| **MTEB** | Massive Text Embedding Benchmark (Muennighoff et al., 2023): dozens of tasks (retrieval, classification, clustering, similarity…) and the leaderboard most embedding models are chosen from. A starting point, not an answer: it averages many tasks and public sets can leak into training. | |
| **sentence-transformers** | Hugging Face library for bi-encoders (`SentenceTransformer`), cross-encoders (`CrossEncoder`), their losses (`MultipleNegativesRankingLoss`, `MatryoshkaLoss`), their training (`SentenceTransformerTrainer`, `CrossEncoderTrainer`) and embedding quantization. (NB 21) | |

## Applications: LangChain and RAG

| Term | Meaning | Spanish docs |
|---|---|---|
| **RAG (Retrieval-Augmented Generation)** | Retrieving relevant chunks of your documents and passing them to the LLM as context. (NB 10, `scripts/rag_demo.py`) | |
| **Chunking** | Splitting documents into (overlapping) pieces before indexing them, e.g. with LangChain's `RecursiveCharacterTextSplitter`. | troceado |
| **Runnable** | LangChain's common interface: every component (prompt, model, parser, retriever, function wrapped in `RunnableLambda`) has `invoke`, `batch` and `stream` (plus async versions), so they can be composed and traced the same way. | |
| **LCEL (LangChain Expression Language)** | Composing Runnables with `\|` (`prompt \| llm \| StrOutputParser()`). `RunnableParallel` runs branches on the same input, `RunnablePassthrough` forwards it unchanged, `.assign(...)` adds keys to a dict. | |
| **Vector store** | A database of embeddings that returns the nearest neighbours of a query vector: `FAISS` and `InMemoryVectorStore` in the course; pgvector, Qdrant or Weaviate in production. | almacén vectorial |
| **Retriever** | A Runnable that maps a query string to a list of `Document`s. `vector_store.as_retriever(search_kwargs={"k": 4})`, `BM25Retriever`, `EnsembleRetriever` and `MultiQueryRetriever` are all retrievers. | recuperador |
| **Dense retrieval / BM25 / hybrid** | Search by embeddings (semantic), by terms (lexical), or both combined. | búsqueda densa / léxica / híbrida |
| **RRF (Reciprocal Rank Fusion)** | Fusing rankings by summing `1/(60 + rank)`. It uses only ranks, not scores, so it needs no calibration. With equal weights, a much weaker retriever can drag a strong one down (NB 21: BM25 + fine-tuned bi-encoder 0.735 nDCG@10, against 0.762 for the bi-encoder alone). | |
| **EnsembleRetriever** | LangChain retriever (in `langchain_classic` in LangChain 1.x) that runs several retrievers and fuses their rankings with **weighted RRF**. The course combines BM25 and FAISS with weights 0.5 / 0.5. | |
| **Reranker / cross-encoder** | A second, more expensive stage that rescores the top candidates of a fast retriever by reading query and document together. An LLM can play the role, but it is not always worth it: in recommendation, a small LLM re-ordering a collaborative model's list made it worse (NB 12 in v2), and the current version uses a LambdaMART ranker. In NB 21, two general cross-encoders did not beat a fine-tuned bi-encoder on SciFact (ms-marco-MiniLM 0.692, bge-reranker-base 0.731 at best, against 0.735 without a reranker). See **cross-encoder**. | reordenador |
| **recall@k / hit@k / MRR / nDCG** | Retrieval metrics: is the right document in the top-k?, inverse rank of the first correct one, and discounted cumulative gain by position. **recall@k** is the share of a query's relevant documents found in the top k (hit@k when there is only one); **nDCG@k** gives a relevant document at rank r a gain of `1/log2(r+1)` and divides the sum by the best possible score for that query, so it rewards putting relevant documents first. nDCG@10 is the headline metric of BEIR and MTEB retrieval; recall@100 is what a reranker can work with. `rag_demo.py` reports them at file level and at *evidence* level (does the chunk actually contain the answer?). (NB 10, NB 12, NB 21) | |
| **Faithfulness / groundedness** | Whether the answer is supported by the retrieved context (rather than made up). | fidelidad |
| **RAGAS** | Library for evaluating RAG with an LLM as judge. Its four core metrics: **faithfulness** (are the answer's claims supported by the retrieved context?), **answer relevancy** (does the answer address the question? measured by generating questions back from the answer and comparing embeddings), **context precision** (are the relevant chunks ranked high?) and **context recall** (does the retrieved context cover the reference answer?). The last two need a reference answer. (NB 10, NB 13, `rag_demo.py --ragas`) | |
| **LLM-as-judge** | Using an LLM to score or compare answers (pairwise, with a rubric). Position and length biases must be controlled, and the judge must be validated before it is trusted. | LLM como juez |
| **Judge strength** | How capable the judge is relative to the system it grades. A weak judge does not only add noise: it can invent differences between systems. In NB 10, the 3B model grading itself reported faithfulness 0.38 → 0.54 between dense and hybrid retrieval; with `qwen2.5:7b` as the judge, 0.87 for both. Rule: a judge stronger than the system, kept fixed while comparing versions (`config.judge_model()`, `JUDGE_MODEL`). | fuerza del juez |
| **Structured output** | Forcing outputs that satisfy a schema. In LangChain, `llm.with_structured_output(PydanticModel)` uses the provider's tool calling or JSON mode and returns a validated object. (NB 11) | salida estructurada |
| **Constrained decoding** | The server turns the schema into a grammar and, at every step, masks the tokens that would break it, so the output is always valid (in Ollama, `method="json_schema"`). It guarantees the shape, not the content. With a large enum it is required: in NB 17, with 77 intents, `function_calling` gave 181 invalid outputs out of 231 and `json_schema` none; in NB 11, on a small schema, function calling was the more reliable method. (NB 11, NB 13, NB 17) | decodificación restringida |
| **Tool calling / function calling** | The model returns a structured call (`name` + JSON arguments) that your code executes. In LangChain a tool is a function decorated with `@tool`, and `llm.bind_tools(...)` exposes it to the model. (NB 11) | llamada a herramientas |
| **Agent loop** | Model → tool → observation → model loop, with a step limit. `create_agent` from `langchain.agents` builds it on LangGraph. | bucle de agente |
| **Middleware (LangChain agents)** | Hooks that wrap the agent's model and tool calls to add behaviour without rewriting the loop: `ModelCallLimitMiddleware` / `ToolCallLimitMiddleware` (budgets), `HumanInTheLoopMiddleware` (approval before a tool runs), `ToolErrorMiddleware` (turn tool exceptions into messages), `SummarizationMiddleware` (compress long histories), or your own `AgentMiddleware`. (NB 11, 14, 16) | |
| **Human-in-the-loop / confirmation gate** | Asking for approval before running actions with side effects (payments, deletions, sending messages). | compuerta de confirmación |
| **Prompt injection** | Malicious text inside the data (a web page, an email, a document, a tool result) that tries to give orders to the model. (NB 11, 13, 14, 16) | inyección de prompts |
| **Indirect prompt injection** | The instruction arrives inside content the model reads while doing its job (a file, a page, a tool result), not from the user. Prompts and filters lower its success rate; isolation (no secrets, no way to send data out) bounds the damage when it succeeds. (NB 14) | inyección de prompts indirecta |
| **Semantic cache** | Reusing answers to *similar* questions (by embedding similarity). Risk: *false hits*. (NB 13) | caché semántica |

## Recommender systems

| Term | Meaning | Spanish docs |
|---|---|---|
| **Recommendation funnel** | The staged architecture of an industrial recommender: **candidate generation** (millions to hundreds, cheap, measured by recall), **ranking** (hundreds to tens, many features, measured by nDCG) and **re-ranking** (rules, diversity, exploration, explanations). (NB 12) | embudo de recomendación |
| **Candidate generation / retrieval** | The first stage of the funnel: several cheap sources (sequential model, two-tower + ANN, co-occurrence, content, popular lists) whose **union** forms the candidate set. Its recall is the ranker's ceiling: what is not retrieved cannot be ranked. (NB 12) | generación de candidatos |
| **Sequential recommender (SASRec)** | Recommendation as "next-item prediction" with a causal transformer over the user's history; the vocabulary is the catalog. It trains better with the full softmax than with sampled negatives; at the scale of millions, **sampled softmax with the logQ correction** (subtract from each logit the log of its sampling probability). (NB 12) | recomendador secuencial |
| **Two-tower model** | Two networks that map user and item into the same space; the score is their dot product. Because the item tower does not depend on the user, its vectors are precomputed and served from an ANN index. With **id dropout** (hiding the id at random during training) it learns to place new items from their content. (NB 12) | modelo de dos torres |
| **ANN / HNSW** | *Approximate nearest neighbours*: indexes that return almost the same neighbours as exact search in far less time. HNSW is the hierarchical-graph one (FAISS, ScaNN, vector databases); its recall against exact search is a quality knob of its own. (NB 10, 12) | búsqueda aproximada de vecinos |
| **Learning to rank** | Training a model to order items: **pointwise** (predict each label on its own), **pairwise** (prefer the positive to each negative, RankNet) or **listwise** (optimise the quality of the whole list). (NB 12) | aprendizaje de ranking |
| **LambdaMART** | Gradient-boosted trees whose gradients are RankNet's pairwise gradients weighted by how much nDCG would change if the two items were swapped. The default industrial ranker; in LightGBM, `objective="lambdarank"`. It only adds something over a strong first stage when it has many queries from a later period and features that stage cannot see. (NB 12) | LambdaMART |
| **Cold start** | Recommending items (or to users) with no interaction history. Collaborative models cannot: the item's row was never trained. Content (text, metadata) places the item and exploration gives it exposure. (NB 12) | arranque en frío |
| **Exploration slot / bandit** | Reserving positions in the list for new or uncertain items, to learn what they are worth (the exploration/exploitation dilemma). *Bandits* ($\varepsilon$-greedy, UCB, Thompson sampling, contextual ones like LinUCB) decide it adaptively; a fixed slot is the minimal version you can measure offline. (NB 12) | ranura de exploración |
| **MMR (Maximal Marginal Relevance)** | Build the list greedily, each time picking $\lambda \cdot$ relevance $- (1-\lambda) \cdot$ maximum similarity to what is already chosen. With $\lambda = 1$ it is the plain ranking; lower means more diversity. (NB 12) | relevancia marginal máxima |
| **Intra-list diversity** | One minus the mean pairwise similarity of the items in a list (in NB 12, genre Jaccard). Offline it can only look neutral or worse for accuracy; its benefit is measured online. **Calibration** (Steck, 2018) also asks the list's genre mix to resemble the history's. | diversidad intra-lista |
| **Leave-last-out / leave-last-two** | A per-user time split: the last event is the test target (and the one before, the validation target); everything earlier is history. A random split would leak the future. (`recsys.temporal_split`, NB 12) | dejar fuera el último |
| **Full ranking vs sampled metrics** | Ranking the target against **the whole** catalog or against ~100 random negatives. Sampled metrics inflate the numbers and can flip which model looks best (Krichene and Rendle, 2020). (`recsys.target_ranks`, NB 12) | ranking completo frente a métricas muestreadas |

## Agents and LangGraph

| Term | Meaning | Spanish docs |
|---|---|---|
| **Workflow vs agent** | In a workflow the code fixes the control flow and the LLM fills in steps; in an agent the LLM chooses the next step itself, in a loop. Start with the simplest one that works. (NB 14) | workflow frente a agente |
| **StateGraph** | LangGraph's builder for a graph whose nodes read and update a shared, typed **state** (a `TypedDict`, or `MessagesState` for chat). `builder.compile()` turns it into a Runnable. (NB 14) | |
| **Node** | A function `state -> partial state update` in a LangGraph graph: an LLM call, a retrieval, a tool, plain Python. | nodo |
| **Edge / conditional edge** | An edge fixes the next node (`add_edge("a", "b")`, from `START` or to `END`). A conditional edge (`add_conditional_edges`) calls a function of the state that names the next node: routing, loops, retries. | arista / arista condicional |
| **Checkpointer** | Saves the graph state after every step (`InMemorySaver` in the course; SQLite or Postgres in production). It gives a graph short-term memory, lets it resume after a failure or a pause, and enables time travel. | |
| **Thread (`thread_id`)** | The key under which a checkpointer stores one conversation: `config={"configurable": {"thread_id": "..."}}`. Same thread = same memory. | hilo |
| **Store** | LangGraph's long-term memory: a key-value store organised in namespaces (e.g. `("users", user_id)`), shared across threads, with optional semantic search when given an embedding model (`InMemoryStore`). | |
| **Interrupt** | `interrupt(value)` pauses a graph inside a node and returns `value` to the caller; the run resumes with `Command(resume=...)`. Needs a checkpointer. The basis of human-in-the-loop in LangGraph. | interrupción |
| **`recursion_limit` / agent budget** | Hard limits on one agent run: LangGraph's `recursion_limit` caps the number of steps, and the call-limit middlewares cap model and tool calls. When one is hit the run stops instead of looping. | presupuesto del agente |
| **Plan-and-execute** | Pattern that first asks the LLM for a numbered plan, then runs each step with a tool-using agent and finally synthesizes the answer. Inspectable and approvable. (NB 14) | |
| **Reflection / verifier** | Draft → verify → revise loop. The verifier checks the draft and returns feedback; code (tests, schema validators) is far more reliable than an LLM critic. (NB 14) | reflexión / verificador |
| **Router** | A node that sends each request to one specialist (a sub-agent or a chain), by an LLM classification or by embedding similarity. It is a classifier and is evaluated as one. (NB 13, 14) | enrutador |
| **Supervisor / agents as tools / orchestrator-workers** | A multi-agent design in which a supervisor agent calls specialist agents as if they were tools, reads their answers, may call again, and writes the final reply. Control always returns to the supervisor, and its cost includes every worker's model calls. (NB 14) | supervisor |
| **Handoff** | A multi-agent design in which the active agent transfers the conversation to another agent, which takes over; whoever finishes answers. What the receiving agent sees (context engineering at the handoff) decides whether it works. (NB 14) | traspaso |
| **Swarm** | A team of agents connected only by handoffs, with no central supervisor (OpenAI's Swarm and Agents SDK, `langgraph-swarm`). | |
| **`Command` / `graph=Command.PARENT`** | A LangGraph return value that updates the state and names the next node in one go (`Command(goto="billing", update=...)`); it also resumes an interrupt (`Command(resume=...)`). With `graph=Command.PARENT`, returned from a tool inside an agent, the jump happens in the parent graph: that is how a handoff moves control from one agent to another. (NB 14) | |
| **Short-term / long-term memory** | The conversation of the current thread (checkpointer, possibly summarized) vs facts that survive across threads (store, retrieved by similarity). | memoria a corto / largo plazo |
| **Trajectory evaluation** | Scoring the path an agent took (which tools, in which order, how many extra calls), not only its final answer. (NB 11) | evaluación de trayectorias |
| **Code execution / code interpreter** | Letting the model write a program and running it, instead of calling a fixed tool or computing in its head. PAL and Program of Thoughts (2022) moved the arithmetic of reasoning into code; CodeAct (2024) makes code the agent's action format. (NB 14) | ejecución de código |
| **Execution feedback** | Returning the result of running the code (output, traceback, "nothing was printed") to the model so it can fix it and try again. It fixes crashes, not code that runs and computes the wrong thing. (NB 14) | feedback de ejecución |
| **Agent-computer interface (ACI)** | The design of tools around how a model reads and writes, not how a person does: concise output, explicit messages for errors and empty results, guardrails such as an editor that rejects invalid edits (SWE-agent, Yang et al., 2024). (NB 14) | interfaz agente-ordenador |
| **Sandbox** | An isolated environment for running untrusted code (here, model-written code): no secrets, no network, its own filesystem, a timeout and resource quotas. Its strength depends on the layer that enforces it: a process, a container, a user-space kernel or a VM. (NB 14) | |
| **Audit hook (PEP 578)** | A Python function registered with `sys.addaudithook` that sees runtime events (`open`, sockets, subprocesses, `ctypes` loads) and can veto them by raising. Useful for logging and as a tripwire, but not a security boundary: native code bypasses it. (NB 14) | |
| **gVisor / microVM (Firecracker)** | Stronger isolation than a container, which shares the host kernel. gVisor is a user-space kernel that intercepts the sandbox's system calls; a microVM (Firecracker, behind AWS Lambda and E2B) is a minimal virtual machine with its own kernel that boots in a fraction of a second. | |

| Term | Meaning | Spanish docs |
|---|---|---|
| **LangSmith** | LangChain's platform for tracing, monitoring and evaluating LLM apps. With `LANGSMITH_TRACING=true` and an API key, every LangChain / LangGraph call, and every function decorated with `@traceable`, is recorded. Optional in the course. (NB 15) | |

| **Project** | The LangSmith container that traces are sent to (`LANGSMITH_PROJECT`, or `setup(project=...)` per notebook). Dashboards and filters work per project. | proyecto |
| **Dataset** | A versioned set of examples (inputs + reference outputs) stored in LangSmith for offline evaluation. | |
| **Experiment** | One scored run of your app over a dataset (`evaluate(target, data=..., evaluators=[...])`). Comparing two experiments compares two versions of the app on the same examples. | experimento |
| **Evaluator** | A function that scores a run, with the signature `(inputs, outputs, reference_outputs) -> score`: a heuristic, a code check, or an LLM-as-judge. Used offline in experiments and online on production traces. | evaluador |
| **Feedback** | A score or comment attached to a run (`client.create_feedback(run_id, key, score=...)`): user thumbs, an evaluator's grade, a heuristic. The online-evaluation signal. | |
| **OTel GenAI semantic conventions** | Standard OpenTelemetry attribute names for LLM telemetry (`gen_ai.request.model`, `gen_ai.usage.input_tokens`, ...), so traces can go to any backend. LangSmith can ingest and export OpenTelemetry. | convenciones semánticas GenAI |

| **SLO (Service-Level Objective)** | A target for a service metric, e.g. "p95 < 2 s, error rate < 1 %". Violations trigger alerts. For serving, SLOs are set on TTFT and TPOT percentiles (e.g. TTFT p95 < 1 s, TPOT p95 < 50 ms). (NB 15, 23) | objetivo de nivel de servicio |
| **PII redaction** | Replacing personal data (e-mails, phone and card numbers, API keys) with placeholders before prompts and responses reach logs or traces. (NB 15) | redacción de PII |
| **Head sampling** | Deciding at the start of a trace whether to keep it as a whole (in LangSmith, `LANGSMITH_TRACING_SAMPLING_RATE=0.1` keeps 10 % of traces). *Tail sampling* decides at the end, e.g. to keep every error. | |
| **Bootstrap confidence interval** | Resample the per-example scores with replacement (say 2,000 times), recompute the mean each time and take the 2.5 % and 97.5 % quantiles: a 95 % interval without assuming any distribution. With 20 questions it comes out wide, and that is information. (`evaluation.bootstrap_ci`, NB 10, 12) | intervalo de confianza bootstrap |
| **Paired bootstrap** | The same resampling applied to the per-example differences between two systems evaluated on the same examples (questions, users). Pairing cancels the variation from how hard each example is; if the interval of the difference excludes 0, the difference is unlikely to be noise. (`evaluation.paired_bootstrap_diff`, NB 10, 12) | bootstrap pareado |

## Safety and guardrails

| Term | Meaning | Spanish docs |
|---|---|---|
| **Jailbreak** | A prompt that gets an aligned model to do what its safety training taught it to refuse. Unlike prompt injection, which attacks an *application* through the data it reads, a jailbreak attacks the model's own values, usually from the user's turn. (NB 22) | jailbreak |
| **Competing objectives** | One of the two failure modes of safety training named by Wei et al. (2023): the model was trained both to follow instructions and to refuse harm, and a prompt sets the two against each other. Prefix injection and refusal suppression exploit it. (NB 22) | objetivos en competencia |
| **Mismatched generalization** | The other failure mode of Wei et al. (2023): safety training covered fewer situations than capability training, so a request wrapped in fiction or role-play, translated or encoded falls outside what refusal training saw, while the model can still do the task. (NB 22) | generalización desajustada |
| **Prefix injection** | A jailbreak that asks the model to begin its answer with an affirmative phrase; once the first tokens comply, continuing is the likely text. In NB 22 it breaks `qwen2.5:3b` on 64 % of JailbreakBench's behaviours, against 4 % when asked directly. | inyección de prefijo |
| **Refusal suppression** | A jailbreak that forbids, as rules for the answer, the apologies, disclaimers and words that refusals are made of. In NB 22 it reaches 24 % attack success. | supresión del rechazo |
| **Over-refusal / exaggerated safety** | Refusing safe requests that only *sound* harmful (killing a process, shooting a photo, the plot of a crime novel), a shortcut learned in refusal training. It costs users and teaches them to work around the system. In NB 22, 17 % of safe XSTest prompts for `qwen2.5:3b` and 5 % for `qwen2.5:7b`. | sobre-rechazo / seguridad exagerada |
| **Refusal rate** | The share of prompts a model refuses. On harmful prompts, higher is safer; on safe prompts it is the over-refusal rate, and lower is better. Usually scored with a keyword judge or an LLM judge, which must be validated on human labels (NB 22: 89.7 % agreement for the keyword judge, 70.0 % for a 7B LLM judge). | tasa de rechazo |
| **Attack success rate (ASR)** | The share of harmful requests that produce a harmful response. A reply that does not refuse is not necessarily harmful, so ASR is scored with a harmfulness judge (HarmBench's classifier, JailbreakBench's judge, StrongREJECT's rubric, Llama Guard), not with refusal detection. (NB 22) | tasa de éxito del ataque |
| **StrongREJECT** | A jailbreak benchmark and grading rubric (Souly et al., 2024) that scores how *useful* a jailbroken answer really is, after showing that "did it refuse?" scoring overstates jailbreak success. | StrongREJECT |
| **Guard model** | A separate classifier placed in front of the model (input filter) or behind it (output filter) that labels prompts or replies as safe or unsafe. Cheap and independent of the model it protects, so one guard covers every model behind it; it has its own false positives and misses. Llama Guard, ShieldGemma and Granite Guardian are open ones; the OpenAI moderation endpoint, Azure AI Content Safety and Amazon Bedrock Guardrails are managed services. (NB 22) | modelo guardián |
| **Llama Guard** | Meta's family of guard models (Inan et al., 2023): an LLM fine-tuned to answer `safe` or `unsafe`, plus a hazard category, for a user prompt or an assistant reply. Llama Guard 3 uses the MLCommons taxonomy S1–S14 (violent crimes, non-violent crimes, sex crimes, child exploitation, defamation, specialized advice, privacy, intellectual property, weapons of mass destruction, hate, self-harm, sexual content, elections, code-interpreter abuse). In NB 22, `llama-guard3:1b` through Ollama flags 95–100 % of the harmful requests and 8 % of the safe XSTest prompts, at 39–62 ms per prompt. | Llama Guard |
| **Red-teaming** | Attacking your own system on purpose, by hand or with tools (PyRIT, garak, promptfoo's red-team mode), to find the prompts that break it before users do. Every successful attack goes into the test set. (NB 22) | red-teaming |
| **GCG (Greedy Coordinate Gradient)** | An automated jailbreak (Zou et al., 2023) that optimizes an adversarial suffix token by token with gradients from an open model; the suffixes often transfer to other models. Not run in the course. | GCG |
| **PAIR (Prompt Automatic Iterative Refinement)** | An automated black-box jailbreak (Chao et al., 2023) in which an attacker LLM rewrites a prompt in a loop, guided by the target's replies and a judge's score, until it works, often within about twenty queries. Not run in the course. | PAIR |
| **XSTest** | A test suite for exaggerated safety (Röttger et al., 2024): 250 safe prompts built to trip refusal shortcuts (homonyms, figurative language, safe contexts, questions about the privacy of fictional people) and 200 unsafe contrast prompts. Its authors also published human-labelled model replies, which NB 22 uses to validate its refusal judge (`Paul/XSTest`, `natolambert/xstest-v2-copy`). | XSTest |
| **JailbreakBench** | An open benchmark for jailbreaks (Chao et al., 2024): 100 harmful behaviours in ten categories, each with a target string and a benign twin on the same topic, plus a leaderboard and a standard judge. NB 22 uses the behaviours, the targets and the twins (`JailbreakBench/JBB-Behaviors`). | JailbreakBench |

## MCP

| Term | Meaning | Spanish docs |
|---|---|---|
| **MCP (Model Context Protocol)** | Open protocol that standardizes how LLM applications get tools, data and prompts from external programs, over JSON-RPC 2.0. (NB 16, `scripts/mcp_server.py`) | |
| **MCP host / client / server** | The host is the user-facing app (Claude Code, Claude Desktop, an IDE, your agent); it runs one client per server; the server is the program that exposes capabilities. | |
| **Tool / resource / prompt (MCP)** | The three server primitives: tools the model calls, read-only resources the application loads into context (fixed URIs or URI templates like `docs://{name}`), and prompt templates the user picks. | |
| **Tool annotations** | Hints a server attaches to a tool (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) so the host can decide, for example, to ask for confirmation before a destructive call. They are hints, not guarantees. | anotaciones de herramientas |
| **FastMCP** | The high-level server API of the official MCP Python SDK (`mcp.server.fastmcp.FastMCP` in 1.x): `@server.tool()`, `@server.resource(uri)` and `@server.prompt()` turn functions into primitives, deriving the JSON Schema from type hints and the description from the docstring; `server.run()` serves stdio, `server.run(transport="streamable-http")` HTTP. | |
| **MCP adapters (`langchain-mcp-adapters`)** | Library that turns the tools of one or more MCP servers into LangChain tools: `MultiServerMCPClient({...}).get_tools()`, ready for `create_agent`. `tool_name_prefix` namespaces tools from different servers. (NB 16) | adaptadores MCP |
| **JSON-RPC request vs notification** | A request has an `id` and always gets a response (`result` or `error`); a notification has no `id` and never gets one (e.g. `notifications/initialized`). | petición / notificación |
| **Protocol error vs tool error (`isError`)** | A JSON-RPC `error` means the request itself was wrong (unknown method, bad params); a result with `isError: true` means the tool ran and failed, so the model can see it and retry. | error de protocolo / de herramienta |
| **stdio transport** | The host launches the server as a subprocess and exchanges one JSON message per line on stdin/stdout. stdout is reserved for the protocol: logs go to stderr. | transporte stdio |
| **Streamable HTTP transport** | The server listens on one HTTP endpoint (e.g. `/mcp`); the client POSTs JSON-RPC messages and the server answers with JSON or an event stream, keeping a session with the `mcp-session-id` header. For remote or shared servers. | transporte Streamable HTTP |
| **Tool poisoning** | Attack where a malicious MCP server hides instructions in a tool's description (read by the model, rarely by the user) or changes it after approval. Mitigations: allowlists, namespacing, reviewing descriptions, confirmation for risky tools. | envenenamiento de herramientas |
| **Sampling (MCP)** | A server-to-client request (`sampling/createMessage`) in which the server asks the host's model for a completion, so it needs no model or API key of its own. The host can show the request, change the model, cap the tokens or refuse. (NB 16) | |
| **Elicitation (MCP)** | A server-to-client request (`elicitation/create`) that asks the *user*, not the model, for structured input or a confirmation described by a JSON schema; the answer is accept, decline or cancel. Not for passwords or secrets. (NB 16) | |
| **Roots (MCP)** | The folders or repositories a client tells a server it may work in (`roots/list`). Advisory: a cooperative server stays inside them, a malicious one can ignore them. (NB 16) | |
| **Resource server / authorization server** | OAuth roles. The authorization server issues access tokens; the resource server (a remote MCP server) accepts requests that carry a valid token for it and answers `401` with `WWW-Authenticate` otherwise. (NB 16) | servidor de recursos / de autorización |
| **Protected-resource metadata (RFC 9728)** | A JSON document a resource server publishes under `/.well-known/oauth-protected-resource`, naming the authorization servers it trusts and the scopes it supports; the `WWW-Authenticate` header of a 401 points to it. (NB 16) | metadatos del recurso protegido |
| **Bearer token** | An access token sent as `Authorization: Bearer <token>`: whoever holds it is authorized, so it is kept short-lived, scoped, out of logs and command lines, and validated (signature, expiry, scope, audience) on every request. (NB 16, `mcp_server.py --require-token`) | |
| **Token passthrough** | The anti-pattern, forbidden by the MCP spec, of a server accepting tokens issued for another service or forwarding the client's token to downstream APIs. It turns the server into a confused deputy; audience validation (RFC 8707 resource indicators) prevents it. (NB 16) | |
